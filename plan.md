# Gracia (Python): plan

A short plan, meant to be adjusted as we go. We build in small steps, each with tests, and decide things when we get to them. Use ruff and ty to check and navigate the code.

## What it is

A repository platform for academic and heritage collections, built on RDF but storing it in a way that is easy to query and serve. Everything is a resource: a subject URI together with the blank nodes embedded in it. Resources live in an embedded DuckDB database, are validated by SHACL shapes, and are served as RDF (JSON-LD, Turtle, ...) and as HTML pages rendered with XSLT.

## Where we are

Terms: the **Application** (the database and the web app) holds **Repositories**; a repository holds **Records**, each of a **Type** (`rec:person:23` is record 23 of the type `person`; in Python `res_type`), and a record holds its **Resource**, the thing it describes (`gracia:resource`, a blank node; named by `gracia:resource_uri`, an ARK).

The core library, CLI and a first web app exist (`src/gracia`, 1,039 tests):

- **Storage.** Flattened triples in DuckDB: one row per value, columns `s, loc, p, o, lit, lang, dt`, all strings (`loc` is a list). `s` is the subject (the record), `p` the predicate of the value, `o` the object when it is a uri, `lit`, `lang` and `dt` the literal. `loc` says where in the record the value sits: `[]` for a property of the record itself, else alternating predicate and blank node label down to the blank node that has the value (`[p1, '_:1', p2, '_:2']`), so `len(loc) = 0` is a top-level row and `p` is always the last predicate. Blank nodes are `_:1`, `_:2`, ... numbered per record (outer ones first); lists are positional (`rdf:_N`); a blank node used twice is stored once per use. `g` is a label on the rows, last and not used yet. There is no dictionary: uris are stored as they are, and DuckDB's own dictionary and FSST compression keep them small. `Store.sort()` (`gracia sort`) rewrites the table in the order of `(s, loc, p)`, so the rows of a type lie in a few row groups and a query for a type skips the rest (DuckDB keeps only the first 12 bytes of a string in a row group's min and max, so the type name has to be inside them: `rec:person:` is). The namespace prefixes that feed the serializers are the settings of the `ns_prefix` extension, not a table.
- **Import and export.** `pyoxigraph` parses and serializes (Turtle, TriG, N-Triples, N-Quads, RDF/XML, N3, JSON-LD), streamed into DuckDB through the appender: about 2.3 s per million triples. Raw export is streaming too.
- **Resources as Datasets.** `Store.get(uris)` and `Store.put(dataset)` use a `pyoxigraph` `Dataset`. `put` replaces each resource as a whole. `gracia.utils.graph.Graph` wraps that dataset with the helpers (`extract`, `subjects`, `orphaned_nodes`, ...) and is what `Store.get` returns.
- **Writes.** Load (replaces by resource; there is no load that only adds), delete (a separate, explicit action). Nothing is deleted implicitly.
- **Repositories.** A repository is a DuckDB schema; its id is the schema name, and each schema holds its own `triples` and `ids` tables and macros, so nothing is shared. What lives as long as the process is in the Pyramid registry: `registry["database"]` (`Database`, `database.py`: the DuckDB connection or the address of the owner, the known repositories, `cursor()`), `registry["cache"]` (`Cache`, with the etags, slugs and types it keeps in `registry["etags"]`, `registry["slugs"]`, `registry["types"]`) and `registry["indexes"]`. `main.init(registry, ...)` opens them for a process (the web app, the CLI, a job process, a test; `main.shutdown(registry)` closes them, `main.opened(...)` does both around a block, `tests/harness.py` has `open_application(test)`) and returns an `Application(None, registry)`, one with no cursor of its own; for a web request the root factory makes `Application(request.db, request.registry)`, where `request.db` is a cursor of the request, closed when it ends (a finished callback, so also when the answer is an error), and the store of the repository below it is scoped to its schema on that cursor. `Application` has `create_repository`, `list_repositories` and `new_store` (a `Store` on a cursor of its own). `database.py` knows DuckDB and Quack only (`Database`, `RemoteConnection`, the owner side `serve_db`); `Store` (`store.py`) never opens a connection, it is given one (`new_store(database, repo)` makes one), and a `RemoteConnection` makes it a store of a database that an owner has. `main` (DuckDB's default schema) is the default repository, so commands without `--repo` behave as before. Ids are lowercase letters, digits and `_`, starting with a letter, at most 63 characters; some names are reserved (the web app's first path segments and DuckDB's own schemas).
- **CLI.** `gracia repo list`, `gracia repo create ID...`, a global `-r/--repo ID`, `gracia serve-db` (the database owner, served over Quack on localhost with a token file; `serve_db` and the owner-file helpers are in `store.py`, next to `RemoteConnection`, the client), a global `-c config.ini`, `gracia serve` (the web app: waitress, one process, a thread per request), `gracia etags rebuild` (the etags of a repository again, see the section on etags).
- **Web.** `main.py`, Pyramid, by traversal: `GET /` lists the repositories, `GET /<repo-id>/` is 200 with the repository's figures (rows, prefixes) or 404, `GET /<repo-id>/api` is that repository's OpenAPI document, built for the caller. ACLs with default deny, JSON 403 and 404, HTTP Basic against the users of the repository, `security.py`; cookie sessions are still to do. `gracia.main` is an add-on (`config.include`), with `make_config(settings)` shared by the app and the tests.
- **Records, types and the repository's data.** Everything a repository stores is a record, `rec:<type slug>:<n>` (so not tied to the vhost): `rec:person:23`. The scheme `rec:` is ours and the same for every type, so a type name can never collide with a real URI scheme; a record key resolves inside a repository at `/<repo>/rec:person:23`, which redirects to `/<repo>/person/23`. A record has `gracia:type` (its type record) and `gracia:resource`, a *blank node* inside the record that holds the content, so a record and its content are one stored object and one `put` replaces it atomically. `gracia:resource_uri` is where the name the resource is published under goes (an ORCID, a permanent URI); it is required and defaults to an ARK made from the settings of the `ark` extension (`repository.extension("ark").settings`), `naan` (default `99999`, the authority number ARK reserves for tests, so those ARKs are not persistent) and `root_prefix` (default `ir`): `ark:/99999/ir/person/34` for `rec:person:34` (the predicate `predicates/gracia_resource_uri.py`; the core does not know the extension). An empty field in the form is the default, a record stored without one shows it, the records made by the code carry it, and the ARK is stored when the record is made, so the ARKs that were given out never change. See "Extensions" below for the settings and the resolver. The stored subject is always the record key. The number comes from the `ids(type, last)` table of the repository (`Store.mint_id`, one upsert, per type, never reused, retried on a conflict). A type is itself a record of the type `Type` (the type records are `rec:type:1..3`): `gracia:name` (the name of the type), `gracia:slug` (the first path segment), `gracia:class` and `gracia:assets`, the asset spec of the directory with its files (see "Types are packages" below); the `Type` type's own shape is a bit meta. A new repository gets `model/repository.ttl`: **the repository itself is a record**, the one record `rec:repository:1` of the system type `repository` (`rec:type:1`), private like users and groups (administrators only; it cannot be added or deleted), whose content (`gracia:resource`, a blank node of the class `gracia:Repository`) holds `gracia:title` (the repository's own `gracia:` predicate, like `gracia:userid`; its id is the name of its schema), `gracia:types` (an rdf list of the type records), `gracia:assets` and `gracia:schemaTemplate` (its own shape, in `gracia/types/repository/shacl/`) and what it says of its extensions; it has a `gracia:resource_uri` like every record. The Repository node of the tree stays the root (`Repository.record()` is that record, a `Record` made from the repository alone: its type is found from its address, its `__parent__` is only set when traversal reaches it; `record.resource` is the node that holds the content; `Repository.types` are the types it lists, by slug). The types of a new repository are Repository, Type, User and UserGroup (`rec:type:1` to `:4`, a content type is `:5` on), the groups `admin`, `editor` and `manager` (`rec:group:1` to `:3`) and the first user (`rec:user:1`, `gracia:userid`, a salted scrypt hash in `gracia:credentials`, `gracia:memberOf` the admin group). `gracia repo create ID` asks for the admin user id and password (not echoed, asked twice), or takes `--admin` and `--admin-password-file`; an existing repository is not asked about. No base URI is stored anywhere any more. The Settings tab of `GET /<repo>/manage` (permission `manage`) is a Deform form generated from the shape file named by the content's `gracia:assets` by `forms.schema_from_shape` (a subset: plain-URI `sh:path`, `sh:name`, `sh:description`, `sh:order`, `sh:minCount`, `sh:minLength`, `sh:maxLength`; text fields only; the predicates of the properties change a field: the time zone is a drop-down, `predicates/gracia_timezone.py`); a valid POST replaces the properties of the form (the title and the time zone; one left empty is removed) in the content and `put`s the record. Deform's static files are served at `/_static/`.
- **Jobs.** A job is a list of stages, which are Luigi tasks (`gracia/jobs/`), run in a detached process of its own: `Export` (also of graphs and of the queue), `Validate`, `Rewrite`, `PurgeSlugs`, `RebuildEtags`, `UpdateCache`, `ProcessActions` and `IndexRecords` exist. `gracia jobs list | show | log | create | validate | start | stop | clean` and `gracia run <uuid>`; one row in `_gracia.jobs` with the definition and the live progress as JSON; the jobs page, a job panel that other pages include, and the manage pages of a type and of a repository, each with a Jobs tab (a type validates a schema file before it is saved). See the section Jobs.
- **Etags, batches, times.** Every record has an etag, ready in the `etags` table (kept by the writes, in the same transaction; a rename of a university that 660,000 pages are made of takes 0.6 s at 1,000,000 records), and the records of a type, or those that point at a record, are read a page at a time (`?page=N`, page 1 the newest) with their totals. A browser gets a page for a type (the records, with page links) and for a record (its label, type, description and key information, labelled from the shapes). Times are stored in UTC and shown in the time zone of the repository, which is a setting of the repository record. See the sections "Etags, batches and the pages of a listing" and the predicates.
- **Caches, the change queue and search.** What follows the data (see the section on times, caches, the change queue and search): the etag cache and an LMDB cache of the RDF/XML of a record and what it is made of (`cache.py`), a queue of what changed written in the transaction of the write with a worker thread that fires one `RecordsChanged` event per batch (`actions.py`), and a Tantivy index per repository made by an XSLT document (`search.py`, the `search` extension, the job Rebuild search, a search box on the repository page), with a Stats tab on the manage page.
- **SHACL.** `shacl.validate(dataset, shapes, shape=None)` with `pyrudof`, in batches.
- **XSLT.** Saxon chain in memory: flat RDF/XML, then nested RDF/XML with `rdf:parseType="Collection"`, then your stylesheet. An HTML table example is bundled.

## Decisions so far

- A resource is identified by its subject URI.
- Bnode ids carry no meaning. Resources are replaced whole, so renumbering is fine.
- `Dataset` (`pyoxigraph`) is the in-memory object: it holds one resource or many. Any ORM-like wrapper is later syntax on top of it.
- Streaming is for raw export. Records and validation work on in-memory Datasets, in batches.
- XSLT receives RDF/XML (flat, serialized by `pyoxigraph`), nested by a bundled stylesheet; the chain stays in memory.
- Validation is a function over a Dataset and a shapes graph. The cost is mostly per call (about 20 ms), so use batches of thousands.
- Dependencies live in `pyproject.toml` (managed by `uv`); `ruff` for lint and format; tests with `pytest`: `uv run pytest -n 16` (`pytest-xdist`, 833 tests in about 41 s; `-n 8` about 54 s; passed every run at 16 workers, a dozen so far). The tests use random ports and temporary directories, so they run side by side. `-n auto` (32 workers on 32 cores) left a rare failure in the tests that start real processes (a job not found right after it was created, cause not found, not reproduced in 600 calls of the test alone) before the changes below; it has not been tried since. What made it fast, in `tests/conftest.py` and the tests (102 s at 8 workers before, 54 s now): (1) DuckDB gets two threads in a test process (`GRACIA_TEST_DUCKDB_THREADS`), not one per core, which at eight workers was 256 threads on 32 cores; (2) the first repository of a kind that a test makes in a process is built the normal way into a template file and every later one is a copy of that file (making a repository is 127 statements, 200 to 300 ms, and was done 590 times, about a quarter of all the time; `COPY FROM DATABASE` into memory was tried and does not keep the triggers, so the records, the history and the etags silently stop following the triples), and `conftest.prepared(app, key, build)` does the same for a whole starting state (`EditCase`: the repository, the people and an editor, which was two writes and 0.25 s in every one of about 155 tests; its schema files are in one directory per process that every test writes clean); (3) passwords are hashed at the cheapest scrypt cost in the tests (a hash carries its own parameters): HTTP Basic checks the password on every request, 23 of the 26 ms of a request as the admin; (4) `WebCase.client()` builds the app once per test while its settings stay the same (13 ms each time), a new client around it has no cookies; (5) tests that need many records make them in one write (a write costs 0.1 s at any size). Not where the time was: the Pyramid scan and commit (13 ms a test), the first request (14 ms), so a shared registry or `pyramid.testing` doubles would not help. For a `unittest` class `setUp` runs inside pytest's *call* phase, so `--durations` shows no separate setup time: a test that makes one request and takes 0.3 s is a slow `setUp`; and a second `pytest.main` in the same process reloads `conftest.py` with empty template caches, so to see warm numbers run the classes three times in one session (subclasses). Left: a form save is 100 to 150 ms (the write path), so the tests that save through the form take 0.4 to 0.5 s.
- **Pyramid is the web framework** (decided, over FastAPI). Reasons: the permission model (ACLs along a resource tree, default deny, permission names mapped to groups) and the multi-tenant structure (application, then repository, then content type, then resource) are what Pyramid's traversal and ACLs do natively; the registry and `config.include` give extension packages a place to plug in; a sync WSGI stack suits our blocking DuckDB, XSLT and SHACL calls. The public site is server-rendered and heavily cached, so framework speed is not the deciding factor, and FastAPI's draws (typed JSON models, generated JS clients, async) matter little for an RDF API. The library (`Application`, `Store`) stays free of any framework, so this stays cheap to revisit.
- **Followers of the data work from a queue and the current state (decided, 2026-11).** A queue per repository, written in the transaction of the write; a worker thread of `gracia serve` takes it a batch at a time (up to 5,000 records or 20 MB), reads the records as they are, and fires one event per batch; a handler can do a record twice. LMDB for what is kept for a request (the graph cache), Tantivy for search, an XSLT stylesheet for the document; the index definition is fixed for now. Details in the section on times, caches, the change queue and search.
- **The API document is generated per request, for the caller** (`/<repo-id>/api`), not read from a file. Operations are registered with `config.add_api_operation(path, summary, permission)`; the document lists only those the caller holds the permission for, checked against the repository with the same ACLs that enforce access. Hiding a path is documentation, never the protection: the view's permission is. It is sent `Cache-Control: private` and `Vary: Authorization, Cookie`.
- **Forms are generated from the shapes, on the server.** The `Dataset` is the model, the SHACL shapes are the schema of record, and Deform forms (Colander schemas generated from the shapes, for a documented subset) edit it; `shacl.validate` stays the authority. `shacl-form` (browser side) remains the alternative for shapes the generator does not cover. See "Forms, configuration and the object layer". Ordinary forms (login, password change, API keys, creating a repository) use hand-written Colander schemas with Deform; not `pyramid-deform`, `deform_bootstrap` or `cornice` for new code.
- **Caching** of anonymous records is planned separately (an extensive plan exists) and comes later. The design leans on: only anonymous, public renderings; ETags of everything a record reaches (built: the `etags` table, see the section on etags; the file cache is not); no cookie on anonymous responses.

## Web layer: Pyramid

- **Addresses.** Every address the user interface produces is absolute and comes from `request.resource_url(node, *names, query={...})`, never from `resource_path`, `path_url` or a string put together by hand, so that a virtual host in front of the application is followed by every link: form actions, `hx-get`, the `data-*-url` attributes our scripts read, redirects, the job URLs in the JSON (`url`, `log_url`, `logs_url`, `download_url`), the `servers` of the OpenAPI document, the record and ARK resolvers, and the `<link>`, `<script>` and favicon of fanstatic (`base_url=request.application_url`). `tests/test_urls.py` fetches the pages and fails on a relative address in any URL attribute. Not an address we make: the `path` that the JSON error bodies echo (the request's own path). A record is at `.../person/34/` (the trailing slash is what `resource_url` makes; traversal takes both).
- **The tree.** The `Application` (the database owner, `application.py`) is the root, below it a `Repository` node per repository (`resources.py`), below that a `Type` node per type the repository lists in `gracia:types`, by slug, and below that a `Record`: `/<repo>/<slug>/<n>` is `rec:<Type>:<n>`, and must carry `gracia:type` of that type. An unknown repository, type or record is a `KeyError` in traversal, hence a 404 with no extra code. A node reads what it needs through the repository's store (`Repository.store()`, opened on first use, closed when the request ends; `request.store` is the same one). The slugs `api`, `manage` and `_static` are views, so a type with such a slug is ignored. The name of a type is in every record URI, so it cannot change. Every node below a repository (`Type`, `Record`, `Jobs`, `DeformViews`, `DeformView`, `JobRun`, `Resolved`: the base class `resources.Node`) has a `repository` property that walks up `__parent__` to the `Repository` and keeps it (a node lives for one request), so code without a request (a command, a job, an extension) can ask too; `Repository.repository` is itself and the `Application` has none. `request.context.repository` is the way from a view (there is no `request.repository`), and `request.store` is `request.context.repository.store()`.
- **Reaching the data.** `request.root` is the `Application`. `request.store` (a reified request method in `main.py`) is a `Store` on the schema of the repository the request reached (found in the context's lineage), opened on first use and closed in a finished callback; views that never touch it open no cursor, and a request that did not reach a repository gets a `LookupError`. The schema is chosen when the cursor is opened, not during traversal, so the 404 and the list view cost nothing.
- **Types are packages; their files are assets.** Shapes and stylesheets are not in the database: a type is a package under `gracia/types/<slug>/` with `__init__.py` (`includeme(config)`: the record class and views), a directory `shacl/` with its schemas and later `view.xsl`; the repository, a record of the type `repository`, has its schema in `gracia/types/repository/shacl/`. **Schemas are files named `<Type>-<profile>-<revision>.ttl`** (`Person-full-03.ttl`, `Person-minimal-01.ttl`: the type's name as in the record URI, a lower-case profile, a revision of two digits or more), so a type can have several profiles (everything `foaf:Person` has, or just a given and a family name) and a changed schema is a new revision; the type record names the one its records follow in `gracia:schemaTemplate` (`"Person-full-03.ttl"`), so switching revision or profile is a change of that type's data (the Type type's form edits it), and the name must be of this type (`assets.schema_spec` refuses another type's file, a wrong shape of name and `..`). Which schemas exist is not listed (a directory is never listed: overrides), so the type says which one. A type record's `gracia:assets "gracia.types:user/"` names the directory (an asset spec: `package:path/`, or an absolute path), and `gracia/assets.py` resolves `<assets>shacl/<schema>` through Pyramid's `AssetResolver` and caches the parsed shape by file path and modification time; a type whose files cannot be read is logged and has no form. The setting `gracia.types` lists packages besides the ones that are always there to include and to look at for a `TYPE` (the three system types and the subpackages of `gracia.types` are always there); a repository uses the types it lists in `gracia:types`. Changing a shape in git changes it in every repository at once. Customizing: `config.override_asset("gracia.types:user/", "mylib:types/user/")` layers a directory or a single file over a type for the whole deployment (checked: the overriding directory wins file by file, a file it lacks falls through, the overrides belong to the registry of the application so another app in the process is not affected, and `importlib.resources` bypasses them, which is why everything goes through `AssetResolver`); for one repository, point its type record at another prefix. Pyramid's asset system and its overrides are built on `pkg_resources` (setuptools plans to remove it; we already pin `setuptools<81` for Deform and filter the warning), so only Pyramid's resolver is used and nothing here calls it directly. Python that differs per repository would need Zope-style layers: a marker interface put on the request when traversal reaches a repository, with views registered for it (`request_type`); tried in a spike and it works, not built.
- **Jobs are in the registry, stages are Luigi's.** `IJob` (`gracia/interfaces.py`) is a marker; a job a person can start is a class (`gracia.jobs.job.Job`) marked with `@job("validate")` (`gracia.jobs.job`, found by `config.scan`: the package `gracia.jobs.validate`, the entry-point group `gracia.jobs`, the setting `gracia.jobs`), registered as an `IJob` utility; `config.add_gracia_job(name, cls)` does it without the decorator, and two jobs with one name are a conflict at commit. A job has a title, a form (a Colander schema, rendered with Deform) and `spec(repo, params)`, which makes the list of stages. The stages are not registered by us: they are Luigi tasks, found by their class name in Luigi's own register, so importing the module is all it takes (`gracia.jobs.stage.load_modules`: the built-in module, the entry-point group `gracia.stages`, the setting `gracia.stages`).
- **The jobs view and the job panel** (`/<repo>/jobs`, `views/jobs.py`, `templates/jobs.pt`, `templates/job_panel.pt`, `static/scripts/jobs.js`; tests in `tests/test_jobs_view.py`). The page lists the jobs the caller may start (each with a Bootstrap modal holding its Deform form, posted with `fetch`; a form with errors comes back as 422 and is shown again) and includes the *job panel*: a template macro (`panel.macros['panel']`, with `panel_list_url`, `panel_filter` and `panel_watch`) that any page can include. A panel lists the jobs of its list url (`jobs/list`, filtered by `?job=validate&subject=person`), refreshed every second (a row is made once and updated in place, so the sliding bar of a stage that does not know its total is never restarted), and follows one job in a dialog with a bar per stage: batches done of total and how many run now, items processed and passed, what was rejected by reason, a few samples, a download of everything rejected, a Stop job button and a *Details* triangle (`<details>`) that folds open an iframe with the bare log (`logs?embed=1`, about 13 lines high, its own scrollbar, following the end; loaded only while it is open). Starting a job is separate: a modal form, or any button with `data-start-job="<url>"` that posts the fields of the form it belongs to, announces the job with the event `gracia:job-started` and every panel that lists it opens it. Permissions: `list_jobs` and `start_<name>_job` on the `Jobs` node (administrators, and the `groups` of the job: editors and managers by default; a job with `groups = ()` is for administrators), `view_job` and `stop_job` on a `JobRun` node (its creator, stored as `user:<userid>`, and administrators; a job from the command line has no creator). Under the jobs node "not there" is answered 403, like below the other private nodes. Endpoints: `GET jobs/<id>` (the job as JSON), `GET jobs/<id>/download` (the file the job offers, by the name in its row, never a path), `GET jobs/<id>/log?name=luigi|job&offset=N` (at most 64 KB from a byte on, the next offset in `X-Log-Offset`; while the job runs only whole lines are given, because a record can be written in two pieces, and the unfinished one waits for the next read), `GET jobs/<id>/logs[?embed=1]` (the page that follows the log: `static/scripts/joblog.js` asks for what is new every second and appends it, keeps the last 400,000 characters, scrolls with the end while Follow is on, and stops three polls after the job is over; no request is held open, because a streamed response would pin one of the few server threads for as long as someone watches), `POST jobs/<id>/stop` (spawns `gracia jobs stop <id> --by <user>` detached and answers 202). The server hands its jobs the config file it was started with (`gracia.config_file`, set by `gracia serve`) and `gracia.db`; jobs need `serve-db` for more than one worker (not checked for the rest). POSTs are checked to come from this site (`views.same_origin`) until the cookie sessions and CSRF tokens are built.
- **The page to manage a repository** (`/<repo>/manage`, permission `manage`, `views/manage.py` (`RepositoryManage`), `templates/manage.pt`; tests in `tests/test_manage.py`). Both manage pages are one class each in `views/manage.py` (a `Manage` view: `TypeManage`, `RepositoryManage`); the tabs are only the strip of `manage.pt` and a method `pane_<name>` per pane, there is no tab registry. Tab `Types` (first; the types that are installed, each a link to its manage page for those who may manage it, system types marked), tab `Settings` (the Deform form of the repository resource from its shape: the title and the time zone, `gracia:timezone`, a drop-down of the common IANA zone names with an empty choice that means UTC: everything is stored in UTC and shown in this zone; a post must come from this site; saving flashes and goes to `?tab=settings`) tab `Extensions` (below), tab `Predicates` (below) and tab `Jobs` (the jobs about the repository as a whole: `rebuild_etags`, administrators only; `templates/repository_tab_jobs.pt`).
- **Extensions** (`gracia/extensions/`, contract `IExtension` in `interfaces.py`; tests in `tests/test_extensions.py`, `tests/test_ark.py`). An extension is an optional part of a repository: a class in a module of `gracia.extensions` (or of a package named in the setting `gracia.extensions` or in the entry point group `gracia.extensions`), marked `@extension("ark")` and found by `config.scan` (a module-level `includeme(config)` of a scanned module is called too, `extensions.include_modules`). The class is a **named adapter of the repository** (`IRepository` to `IExtension`): `repository.extension(name)` is the extension as it is in that repository (`KeyError` for an unknown name, one object per name per request), `repository.extensions()` are all of them by title. The author declares class attributes `title`, `description` and `settings_schema` (a Colander schema class, a mapping, every field with a `default` and a `missing`; `None` for no settings), and overrides the properties `enabled` (default: the stored flag, else off; an extension may ignore the flag or look at the repository) and `can_disable` (default `True`) when it needs to. An instance has `repository`; properties `enabled`, `can_disable`, `settings` (a fresh plain dict); methods `enable()`, `disable()` (refused when it cannot be turned off; the settings are kept), `save_settings(data)`, `export()`, `import_json(text)` (a JSON number or `true` is taken for a number or boolean field), all raising `ExtensionError` with the reasons; `schema(request)` is the settings schema bound to the repository (so `colander.deferred` works). `enabled` has no setter on purpose (turning on can be refused and writes to the repository). The core builds the Deform form from the schema (`extensions.settings_form(extension, request, **options)`: `gracia.forms.Form`, horizontal), so an extension does not touch Deform's form class. The extension does not touch the data: `extensions/__init__.py` reads and writes one blank node per extension that has a state, in the content of the repository record: `gracia:extension [ gracia:extension_name "ark" ; gracia:extension_is_enabled true ; gracia:extension_settings "{...}"^^rdf:JSON ]` (read once per request, cached on the repository node; a write drops the cache). The settings are the *cstruct* (`schema.serialize`: strings, lists, dicts, a date as ISO text), read back through the types, so the extension gets real Python values and JSON never meets a `date` (`forms.py`: `to_json`, `nulls_to_none` for `colander.null`). **Settings are never migrated**: reading is lenient (a missing setting is its default, an unknown stored key is ignored, a stored value the schema no longer takes is its default and is logged), so an extension has to keep working with the settings of its older versions. What an extension adds, it adds like anything: decorators found by `config.scan` and, when needed, `includeme`; there is no hook object. What is below a repository comes from the registry, not from the repository: `@traversable("key", context=IRepository)` or `@traversable(prefix="key")` on a class or function (`gracia/traversal.py`, `ITraversable` and `IPrefixTraversable`, registered as adapters of the parent like extensions; `config.add_gracia_traversable(factory, name=..., prefix=...)` does the same without a decorator; `jobs`, `deform` and `rec:` are registered that way by the core in `resources.py`; a key a type could have as its slug is refused), and `Repository.__getitem__` asks `traversal.child` and then the types. A class is made with the parent in its `__init__` (the repository, below a repository), a prefix one with the parent and the segment. A view that is only for repositories where an extension is on says so with the view predicate `enabled_extension="ark"` (a repository where it is off answers 404). The tab `Extensions` of the manage page is a card per extension (title, description, enabled or disabled badge, one button, Disable or Enable, Disable greyed out when the extension cannot be turned off, a Settings button when it is on and has settings); the dialog has two tabs, the Deform form with an "Update settings" button and the same settings as JSON in a text area ("Update from JSON"); every button posts to `manage?tab=extensions&extension=<name>` and the name of the button says what to do; a form or JSON that is not right comes back with its dialog open and its button (`data-open`, `static/scripts/manage.js`, which also asks `data-confirm` before a disable). `gracia -r <repo> extensions list | enable NAME | disable NAME | export NAME [-o FILE] | import NAME [FILE]` does the same from the command line. `gracia.forms.RENDERER` puts `templates/deform/` (so far the form with tabs) in front of Deform's own templates for every form; more extended templates are expected (Deform still writes some with Bootstrap 3 classes).
- **The ARK extension** (`extensions/ark.py`). Always on (`is_enabled` is `True`, `can_disable` is `False`): the ARKs that were given out have to keep resolving. Settings `naan` and `root_prefix`, stored when the repository is made (`create_repository(ark=(naan, prefix))`, default `99999` and `ir`). They are not editable yet, a gap that is meant to be closed: changing them means rewriting every `gracia:resource_uri` in the graph, also where one is used as an object, a bulk operation that is not there yet. Until it exists the schema's validators only match `99999` and `ir` (the form, an import and `set_settings` refuse anything else and say so) and the real validators (letters and digits) are commented out beside them; the settings a repository was made with are read, not validated. The resolver is a view named `ark:` on the repository (`@view_config(context=Repository, name="ark:", enabled_extension="ark")`, the rest of the address is `request.subpath`): `/<repo>/ark:/99999/ir/person/34` redirects to the record; an ARK in the form the repository makes is read as it is, any other (a record that names its own `resource_uri`) is found with `Store.find`; a record the caller may not see is 404. `/<repo>/rec:person:34` redirects the same way (`Resolved`, registered as a prefix child).

- **The API document and its browser.** `/<repo>/api` is the OpenAPI document for the caller; the same address with `Accept: text/html` (what a browser asks) is a page (`templates/api.pt`, `static/scripts/apibrowser.js`: every operation with its method, path, summary and permission, and a "Try it" for the GET ones, with an input for each `{name}` of the path; a page answer is shown as a link, JSON is pretty-printed). - **Scripts and styles: `fanstatic` (`gracia/static.py`).** Pages do not write `<script>` or `<link>`; they *need* resources (`static.page.need()` in `views.render`, `jobs_js.need()`, `api_browser_js.need()`, `need_form(form)` for the widgets of a Deform form, from `form.get_widget_resources()`), and a Pyramid tween (`gracia.static.tween_factory`, written for fanstatic's own `NeededResources` and `TopBottomInjector`, because `pyramid_fanstatic` is from 2020) puts them in the `<head>` of HTML responses once each in dependency order, and serves the libraries below `/_static/<library>/:version:<md5>/...` with `Cache-Control: max-age=315360000` (ten years). The version is the md5 of the library's files, so a changed file has a new address and nothing is ever stale (the cache problem of the jobs page); `bundle` turns the files of one library into one request: the site's styles are one file (`bootstrap.min.css;gracia.css`), its scripts one (`bootstrap.bundle.min.js;deform-load.js;jobs.js`), and what Deform's widgets need is one more script (and style) from the `deform` library, which is only on pages that have a form. The scripts wait for `DOMContentLoaded` because they are in the head. Libraries: `gracia` (`gracia/assets/static/`) and `deform` (its static directory: every file of its resource registry is a resource, with jQuery before them, which Deform does not name); a widget that names a file of another package needs a library that is *declared* for it: a `fanstatic.Library` with a `Resource` for the file, registered with `config.add_gracia_library(library)` in the package's `includeme` (or the `fanstatic.libraries` entry point), before the first request, because fanstatic numbers its libraries once (a library added later is an error that says so). Nothing is made on the fly: an earlier version made a library of the directory of any file a widget named, which would have published that whole directory (a type's `shacl/` and `view.xsl`) and renumbered the registry under a lock; a file in no library, or in a library but not a resource of it, is a `LookupError` that says what to declare. A package declares one library for its assets, which also serves the XSLT output of its type (the stylesheet's needs). Setting `gracia.fanstatic.recompute_hashes = true` re-reads the files at every request while developing a script (default: once per process). Not done: our JavaScript and CSS are not minified or compiled (fanstatic can with `compile`/`minified`, when there is a build step); `gracia` and `deform` stay two bundles of each type on a page with a form.
- **Deform views: a form that changes itself (`gracia/views/deform.py`, htmx).** The `schema` select of the validate form follows the `type` select, and only the dependent field says so: `widget=dependent_select("schema-files", depends_on="type")` on the schema node (the form is Deform: Colander schemas, `SelectWidget`s). What it calls is a function next to the form, declared with `@deform_view("schema-files", at="jobs", permission="start_validate_job", form=validate_form)`, `(context, request, values, form, field) -> [(value, label), ...] | html | Response | form`: `field` is the target field (`?field=<name>`, which a widget adds to its own URL; in-process the widget passes its own field; None for a view of the whole form; an unknown name is a 404), so one view can serve several fields. A deform view *always* gets the form it belongs to (a fresh one of the request made by the required `form=` factory, `(context, request) -> deform.Form`, the same the page uses, `Job.form`; or, when a widget calls it while the form renders, that very form). The decorator is Pyramid's `view_config` (venusian, `config.scan`) plus a registration of the function as an `IDeformView` utility under its name (`config.add_gracia_deform_view`; a duplicate name is a conflict): it is served at `/<repo>/deform/<name>` (`/library/deform/schema-files?field=schema&type=person`): a traversal node `DeformViews` below the repository (`deform` is a reserved slug) and a `DeformView` node per registered name, with one generic view (`serve` in the same module, `views/deform.py`) that asks the permission the function was declared with (`permission=`, default `view`) of the node it was declared for (`at="jobs"`, or the repository when `at` is not given) and passes that node as the function's `context`; one namespace, so a deform view can never clash with a type slug, and no endpoint is written per field or per job. Over HTTP it answers `<option>` elements for a list (renderer `gracia-deform`, `templates/options.pt`, `Cache-Control: private, no-store`), a string as it is, a Pyramid `Response` as it is, or *the form*: the function changes the form it was given (fields, widgets) and returns it (`render_fields(form, controls, names)` renders only some fields, as rows with labels and errors but without the `<form>`, fieldset and hidden inputs, to swap one row of a page's own form), and it is rendered with what the browser posted (`render_posted`: `widget.deserialize` then `serialize`, no validation, so no errors on a half-filled form). A field that changes the complete form has `hx-get` the view, `hx-include="closest form"`, `hx-target="closest form"`, `hx-swap="outerHTML"` (not built into a widget yet). The widget puts its htmx attributes on its own select through Deform's own `widget.attributes` (no custom template): `hx-get` the view, `hx-trigger="change from:#<other field's id>"`, `hx-include` that field, `hx-target="this"`, `hx-swap="innerHTML"`; the other select is a plain select. The widget calls the same function directly to render its choices the first time (for what the other select shows: its first choice) and when the form comes back with errors (for what was posted), and `options_validator("schema", "schema-files", depends_on="type")` on the schema (the mapping) refuses on the server a value the view does not offer for the other value, so the browser is never trusted; the `type` field has its own `OneOf`. An unknown view name fails when the form is bound. Form id `form-job-<name>` (`Job.form_id`). The 422 form is put in the page with `htmx.process`. htmx 2.0.11 (0BSD) is vendored in `static/scripts/htmx.min.js`, a resource of the `gracia` library that `jobs.js` depends on. Checked in Firefox with the first version (an endpoint per job, now removed): choosing a type swapped the options and reset the selection; the deform-view version is tested through the app but not yet clicked in a browser. `hx-target` can also be `next .class`, `closest ...`, which matters for nested repeated fields.
- **Flash messages and the session** (`views/__init__.py`, `main.py`; tests in `tests/test_type_manage.py`, class `FlashTest`). `gracia.views.flash(request, message, level="success")` says something on the next page that is shown (after a redirect); `level` is a Bootstrap colour (`success`, `info`, `warning`, `danger`) and the queue of Pyramid's own `request.session.flash`. The layout shows what is waiting, once, as dismissible alerts above the content (`render()` takes them from the session, so every full page does it; a fragment does not). The session is Pyramid's `SignedCookieSessionFactory`: a signed cookie `gracia_session` (HttpOnly, SameSite=Lax, no timeout, never reissued by looking at it) that is only set when something is flashed (a page with nothing to say sets none: a queue is looked at with `peek_flash` and only popped when it has something in it, because a pop counts as a change). The secret is the setting `gracia.session_secret`; without one each process makes its own, so a flash does not outlive a restart or reach another process (set it when there are several workers); `gracia.session_secure = true` marks the cookie Secure behind TLS. The older `?saved=1` of the edit forms is not moved to flashes yet (the repository manage page is). - **System types and content types.** A repository cannot work without four types, `repository`, `type`, `user` and `group`: every repository starts with them (`gracia/assets/model/repository.ttl`). Everything else is a **content type**, a type for a domain, optional and added without a change to gracia: a package with a descriptor and its schemas. `gracia/types/person/` is the first: `__init__.py` has `TYPE = {"name": "Person", "slug": "person", "class": "https://schema.org/Person", "schema": "Person-schemaorg-01.ttl"}` (the shipped person is the schema.org one; the foaf profiles below stay as files, and the tests configure a person on them with `FOAF_PERSON` in `tests/harness.py`: what a type is on is configuration) (and an `includeme` only when the type needs code, a record class or views), `shacl/Person-minimal-01.ttl` is a few strings on `foaf:Person`, and `shacl/Person-full-01.ttl` the fuller profile (the name in two parts required; mailbox, phone, homepage, picture and knows, checked as `mailto:`, `tel:` and `http(s):` URIs; the populate data conforms to it); switching a type to it is done from the manage page, after a Validate (the first part of a schema file name is the name of the type, so `Person-...`, not `person-...`). Content types are found as plain data in three places: the subpackages of `gracia.types` that have a `TYPE` (adding the folder is all), the entry points of the group `gracia.content_types`, and the dotted names in the setting `gracia.types` (`types.available()`). Which ones a new repository gets is the setting `gracia.content_types` (slugs or dotted names); `gracia types add <slug|package>...` adds one to a repository that exists (idempotent: a type record and an entry in the list on the repository resource, in one transaction), `gracia types list` shows the types of a repository (slug, type record, name, class, schema) and `gracia types available` the content types there are. `Application.create_repository(..., content_types=...)` takes them; a descriptor is checked before anything is made, and nothing that goes into the Turtle can break it (`init.type_turtle`).
- **The types are in the registry** (`gracia/interfaces.py`: `IGraciaType`, a marker with documented attributes; `gracia.types.TypeInfo` implements it). The web application registers a utility for every type it knows, under the URI of its class and under its slug: `registry.queryUtility(IGraciaType, "user")` (or the class URI), `registry.getUtilitiesFor(IGraciaType)` for the (name, type) pairs, `known_types(registry)` once each. `config.add_gracia_type(...)` registers one (through `config.action`, so that two types with one class or slug are a conflict at commit), and `config.add_record_class(class_uri, cls)` puts the code of a type (its record class, whose permissions register the edit and add views) on the same object, in either order; `resources.record_class` reads it from there. What the registry holds is what the code knows; which types a repository has, and under which slug, is data in the repository. The commands (`repo create`, `types ...`) and the job processes build their own copy of the registry (`make_config(...).commit()`: about 26 ms) and ask it, as the web application does, so there is one way to find a type, and tests ask the registry what there is instead of importing it (`test_every_type_there_is_has_a_schema_that_loads` covers a content type that is added later). `types.SYSTEM_TYPES` describes the three system types the same way; the template still has them written out, and could be generated from it.
- **The counter of the numbers of a type needs no setup.** `Store.mint_id(slug)` works for any slug (the row appears on the first mint), and every load advances the counters in its own transaction (`sql/advance_ids.sql`, on the staged subjects): a record `rec:<slug>:<n>` that is stored, by an import, a `put` or a copy, moves the counter of its type past `n`, for a type that is registered nowhere too, never down, objects and URIs that are not records do not count. So records that come in with their numbers are never replaced by records made later, and a repository made before the table existed gets it when it first needs it (`ids.sql`). **The records table is the other half of it:** `mint_id` and `last_id` take the greater of the counter and the highest number of the type in `records` and in the history (a deleted record has no row in `records`, but the history has it as deleted, so its number is never used again; `Store.highest_number` is the highest of the records that there are now, which the Rewrite job plans over), so a record that was written outside the store, which `advance_ids.sql` never hears of, is not given out again; the counter still has to be there for numbers that were given out and not saved yet, and for the load that runs while a form holds a number. (`DO UPDATE SET` cannot hold a subquery in DuckDB: the highest is in the inserted row and the conflict takes the greater.)
- **`populate_schemaorg.sh`**: with `gracia serve-db` running and the venv active, a list of gracia commands: it makes the repository `test` (admin / sekretsekret), adds the content types `person`, `organization`, `series`, `collection` and `work` (all on schema.org shapes, `schema:name` is the label of each; the types are `gracia/types/<slug>/` packages found by `types.available()`), and loads dummy content with `gracia import`: 100,000 `schema:Person` records, a 200th of that many organizations, a 1000th of series and of collections and half as many works, which point at each other by resource uri (every record of it follows its shape) (measured: 100,000 records, 700,000 rows, in 2 seconds, a database of 23 MB; running it again replaces them in 4 seconds; a validation job over all of them takes 26 seconds).
- **What the application knows about the files (checksums), kept in the process.** `gracia/assets.py` computes it from the files: `assets.info(spec)` gives the media type, the size and the checksum (`md5:<hex>`, a version for caches, not a signature), cached by the path of the file the overrides give and its modification time and size (so it is computed again only when the file changed, and an override has its own entry); `assets.files_of(prefix, schema, type)` gives the files of a type that exist: the schema file its data names and `view.xsl` (a directory is never listed, because listing an overridden directory shows only the overriding files); `assets.version(prefix, schema, type)` is one digest over those files, which changes when one changes, is added or goes, and when the type switches to another schema, and is what the ETag of a type's records takes in (`Type.assets_version`). Nothing of this is stored in the repositories and nothing is queryable in RDF: a checksum is a function of the file, so every worker computes the same one, an asset belongs to the deployment and not to a repository, and copying it into every repository would cost startup time that grows with the number of repositories (measured with the first design, which recorded the files as Asset records in every repository: 83 ms per repository for an unchanged sync locally, 721 ms through Quack, at every worker start; that design, the Asset type and `gracia assets sync` were removed). `gracia assets list [ID...]` prints the files the types of the repositories use, each once, with checksum, size, media type and spec. `assets.using(registry)` makes the registry of the application current so that its overrides apply outside a request (commands, scripts). The version is in the etag of a page (`views.index.page_etag`). Still to do with the caching: the edges between stylesheets (`type:` imports) as part of the version of a record.
- **`type:` imports in stylesheets.** `xsl:import href="type:person/view.xsl"` (or `xsl:include`) in a stylesheet of one type loads the stylesheet of the type `person` of the same repository. SaxonC takes no resolver written in Python, only XML catalogs (`set_catalog_files`), so `xslt.transform(..., types=repository.resolve_type)` first finds the `type:` addresses in the stylesheets and, recursively, in the files they import, resolves each file by itself (so overrides and per-repository assets apply file by file) and gives Saxon a catalog of exactly those. A path that leaves the type (`..`, a leading slash) and an unknown type or file are errors. The CLI `transform` does not take `type:` imports yet.
- **Record classes and the edit view.** `Type.__getitem__` builds the record through the registry: `resources.Record` unless a class is registered for the rdf class the type describes (`gracia:class`): `config.add_record_class(class_uri, cls)`, called from the `includeme` of the type's package (`gracia/records.py` has the directive). A record class changes behaviour through hooks on `Record` (`extra_fields`, `check`, `apply`, `hidden`) so the generic views serve it unchanged; a view registered for the class overrides the generic one. `GET/POST /<repo>/<slug>/<n>/edit` (permission `edit`) is generic: the form is the record's `subject` field plus the content's fields from the shape file of the type (`forms.fields_from_shape`: single-valued text properties, `sh:pattern` included; lists, URIs and nested shapes get no field and are kept as they are when saving; `hidden` predicates are never shown). Saving replaces the properties of the form and `put`s the record. `UserRecord` hides the credentials, adds a "new password" field (empty keeps the old hash) and refuses a user id that another user has. `edit` goes to admins and to the group `editor`; the User and UserGroup types are admin-only, the Type type can be read by everyone and changed by admins only.
- **Adding records.** `GET/POST /<repo>/<slug>/add` (permission `add`: admins and the `editor` group, except the admin-only types) makes a record with the same form as the edit view: `Type.blank_record()` gives a record of the registered class with no number and no data, so the hooks (`extra_fields`, `check`, `apply`) serve both. Only after the form validates and `check` passes is the number minted (`Store.mint_id`), the skeleton built (`Record.begin`: record type, `gracia:type`, the content blank node typed with the type's class), the data applied and the record stored; a refused form uses no number. It redirects to the new record's edit form. A type whose shape requires something the form can neither fill in nor `supplies` (the Type type: `gracia:class` is a URI) answers 501 with the reasons instead of making an incomplete record. `UserRecord` needs a password when adding. Minting retries on a conflict, also for the first number of a type (the writers race to insert its row).\n- **Permissions per type.** The permission a view asks for comes from the record class: `Record.edit_permission = "edit"` and `add_permission = "add"`; `UserRecord` asks for `super_edit`, `UserGroupRecord` for `manage`. `config.add_record_class` registers the generic edit and add views for a class that asks for something else (add uses a `type_class` view predicate), so an extension names its own permissions the same way. Who holds a permission is the ACLs of the resources: the repository (the `Application`) gives admins everything (`ALL_PERMISSIONS`, which includes `super_edit` and `manage`), the groups `editor` and `manager` `edit` and `add`, everyone `view`; `resources.TYPE_ACLS` holds the entries of the types that differ (User: admins, and the group `manager`, which gets `view` and `super_edit`, so managers add and change users; UserGroup: admins only; both closed with `DENY_ALL`; Type: everyone views, admins change). A normal editor cannot give themselves more rights: only managers can touch users, only admins groups. A permission can be given on its own by one more entry there (a group with only `super_edit` on users), and editors do not get `super_edit` or `manage` through `edit`. Users and groups are never public, at the level of traversal, so no view or class below them can open them: the ACL is on the nodes, every view's permission is checked against it, and no view opts out. The type records that describe them follow the ACL of what they describe, and a record of a private type has the ACL of its type and nothing else, so no flag on the record can open it. What the caller may not see is not there for them: a record they may not view is a `KeyError` in traversal, and a not-found under a node they may not view answers like a forbidden (401/403), so the difference between 404 and 403 does not list the users, the groups or the private type records.
- **Login.** HTTP Basic against the users of the repository the request reaches (`UsersPolicy`, `security.py`): the user is found by `gracia:userid` with `Store.find` (the number in the record URI is minted, so the id cannot be computed), the password is checked against the salted scrypt hash (an unknown user costs as much time as a wrong password), and the names of the user's groups become the principals `group:<name>`, so members of `admin` get what the ACLs give `group:admin`. A user of one repository means nothing in another. There is no site-wide admin: a repository without users cannot be managed (see the gaps). Not logged in, a forbidden view answers 401 with `WWW-Authenticate` (a browser asks for the login); logged in without the permission it is 403. The types User and UserGroup are visible to admins only (their `Type` node denies everyone else), the password hash is never shown. Basic auth: over TLS or on localhost only.
- **Permissions.** `set_default_permission("view")`: a view without a permission still requires `view`. `Application.__acl__` gives admins everything and `Everyone` the `view` permission. A private repository is an ACL entry on its node. `UsersPolicy` can be replaced (API keys, sessions, ...) through the `gracia.security_policy` setting. Lacking a permission is 403, a permitted request for something absent is 404.
- **Add-on structure.** `gracia.main.includeme` sets up the registry and the `add_api_operation` directive, and `config.scan("gracia.views")` finds the views, which register themselves with `@view_config` (`application.py` is the traversal root and `resources.py` holds `Repository`; `views/application.py` has the list and the error pages, `views/repository.py` the figures, the API document and the manage form); `make_config(settings)` builds a configurator the app and the tests both use (settings: `gracia.db`, or an open `gracia.application` for tests, and `gracia.security_policy`). An extension package is one more `config.include(...)`; the including configuration overrides what an included package registered (Pyramid's conflict resolution), and two registrations at one level conflict.
- **Threads.** WSGI under waitress: each request runs in a server thread (default 4, `gracia serve --threads`) with its own `Store` on its own cursor. There is no `def` against `async def` choice.
  - The pool is bounded, so slow work can starve cheap requests. Give long jobs (imports, validation batches, large XSLT) their own executor or process pool.
  - One transaction is one call; writes go through one lock, taken before using a thread for long work.
  - A thread cannot be cancelled when a client disconnects. Use timeouts, and `interrupt()` on the DuckDB connection for slow queries (not tested yet).
  - In-process: a cursor per call. Over Quack: one attached connection per pool slot (below).
  - Python code does not run in parallel across threads; DuckDB releases the lock while a query runs, and whether `pyoxigraph`, Saxon and `pyrudof` do is untested.
- **Streaming responses** for raw export (a response over `Store.export_rows`); in-memory responses for everything that goes through XSLT.
- **Content negotiation** by `Accept` and extension (JSON-LD, Turtle, N-Triples, RDF/XML, HTML), as view predicates (`accept=`).
- **OpenAPI.** Per-request document, as above. `pyramid_openapi3` is optional and only for fixed JSON endpoints (repositories, users, API keys): it is spec-first, loads a spec file once at startup (so content types added at runtime are not validated), refuses to start unless every spec path has a route, serves Swagger UI from a CDN (the template can be replaced to vendor it, untested), pins `openapi-core` to 0.23.x, and validates at about 0.6 ms per request. The explorer page returned 404 in my spike; the cause is unresolved. Its served document can be replaced by our own view (an including configurator can override it without a conflict).
- **Forms.** Server-side with Deform (see the next section). `shacl-form` is kept as an alternative for what the generator does not cover: Pyramid renders the page with the component, receives one Turtle body (CSRF-checked), validates with `shacl.validate` and stores with `Store.put`; its conventions are recorded in the old plan, from its prototype, not re-verified here; pin and vendor it if used.
- **Maintenance notes for Pyramid.** Pyramid 2.1 (March 2026) supports Python 3.12 to 3.14 but releases rarely, and importing it prints a `pkg_resources` deprecation warning (setuptools says it will remove that module); `gracia/__init__.py` filters that one message. WebOb needs `legacy-cgi`, a fork of the stdlib `cgi` module removed in Python 3.13, on 3.13 and newer. Companion packages `cornice` and `pyramid-jinja2` have had no release since early 2024.

## Forms, configuration and the object layer

- **Layers.** The `Dataset` is the model: a resource with its blank nodes and lists. Between it and the views sits a controller layer: the context objects of the traversal tree (`Application`, `Repository`, later content types and resources). They carry `__acl__` and the operations on the model (get, put, delete, validate). Views stay thin and only touch the request and the response, so ACLs live on the contexts, never in views. A thin wrapper over a `Dataset`, driven by the shape, may later give attribute access (`person.name`, `person.affiliation[0].org`); it needs no Colander.
- **The shapes are the schema of record.** From them we derive: validation (`pyrudof`, the authority); Colander schemas and from them Deform forms (server-side, Chameleon templates, Bootstrap 5) for a documented subset: datatypes, cardinality, ranges and lengths, `sh:in`, language-tagged strings with `sh:languageIn`, nested `sh:node`, `sh:order` and `sh:name`; and later a compact JSON representation of a resource, with its JSON Schema for the API document. What forms cannot express (`sh:or`, `sh:and`, `sh:xone`, `sh:not`, qualified shapes, `sh:closed`, complex paths) is left to validation, and the violations are shown on the form.
- **Spike (not in the repository).** Shapes to a Colander schema to a Deform form, then a POST turned into RDF and validated with `pyrudof`, worked for the subset above (about 110 lines), including repeatable and nested fields, with per-field messages. `sh:uniqueLang` was not expressed by the generated schema but was caught by `pyrudof` ("Unique lang failed for lang en"). Not done: filling a form from a stored resource, `sh:class` pickers, ordered lists, URI-valued fields, mapping nested violations to the right field (rudof reports nested violations coarsely).
- **Colander and Deform.** Deform 3.0.1 (2026-02-26): Bootstrap 5 templates, HTML5 validation, updated bundled JS (TinyMCE), Python 3.6 and 3.7 dropped; it needs Chameleon, peppercorn and `setuptools<81`, and still parses posts with `peppercorn.parse`. Colander 2.0 (2023-01) has no releases since but works on Python 3.12 (checked with nested mappings and sequences). Deform ships 25 widgets (text, choices incl. Select2 and Selectize, autocomplete, date and time pickers, rich text, mapping, sequence, file upload) and read-only templates; its bundled JS libraries have not been version-checked, so pin and serve our own copies in production. Extras: `deform_extensions` (2026), `deform_ext_autocomplete` (2020). Abandoned: `pyramid-deform`, `deform_bootstrap` (2013, Bootstrap 2), `deform-jinja2`. Hand-written Colander schemas are needed only for plugin settings and the few ordinary forms; the old repository software's widgets are requirements to rebuild on Deform 3, not code to port line by line.
- **Front-end libraries (checked 2026-11).** Deform 3.0.1 bundles Bootstrap 5.3.2 (latest 5.3.8, 2025-08-26; Bootstrap 6.0.0-alpha.1 appeared 2026-10-08 as the `next` tag, so 5 is the current stable line and a successor is coming), Bootstrap Icons 1.11.1, TinyMCE 6.7.3 (latest 8.10.1), Selectize 0.13.0, pickadate 3.5.6, jQuery 2.0.3 (2013; jQuery versions before 3.5 have known XSS issues) and a jQuery form plugin 3.09. Not version-checked: select2 and typeahead. Plan to serve our own pinned copies.
- **Replacing jQuery.** Deform's own script is small (`deform.js`, 169 lines, 7 jQuery calls). What needs jQuery: the sequence widget (add, remove, reorder with `jquery-sortable`), Select2 and Selectize, autocomplete (typeahead), money masking, the date and time pickers (pickadate), and AJAX submit (jquery.form). Widgets with no JS dependency: text, textarea, select, radio, checkbox, password, mapping, hidden, file upload; rich text only needs TinyMCE. htmx (2.0.11, 2026-09-22; `next` is 4.0.1, so pin it) can take over the server-driven parts: submitting a form and swapping in the re-rendered form with its errors, fetching a freshly rendered sequence item, autocomplete with `hx-get` and `hx-trigger="keyup changed delay:300ms"`. The client-only parts need small jQuery-free libraries: SortableJS 1.15.7 (reordering), Tom Select 2.6.2 (searchable selects, replaces Selectize and Select2), native `<input type="date">` and `type="time"` or a vanilla picker (flatpickr has had no release since 2022), and TinyMCE or another editor. In Pyramid an htmx request is just a view returning an HTML fragment, selected with a `header=` view predicate on `HX-Request`. Our own Bootstrap 5 widgets would be Deform widget classes with their own templates; only needed ones get written. This is for the admin UI only: public records are XSLT-rendered and cached.
- **Wiring up inserted HTML.** Deform already has a mechanism: a widget template registers its init with `deform.addCallback(oid, fn)` (`selectize.pt` does), and `deform.processCallbacks()` / `appendSequenceItem` run it for items added later. For our own widgets, one rule: mark the element (`data-widget="tom-select"`), and a single `htmx.onLoad` function initialises every not-yet-initialised marked element in whatever content just arrived. htmx calls `onLoad` for the first page and for every swapped-in fragment, nested content included, and also processes new `hx-` attributes itself. Alternatives that need no re-wiring: event delegation (one listener on the form) and custom elements (`connectedCallback` fires on insert). Pitfalls: initialising twice (make init idempotent with a marker), cleaning up before removal (`htmx:beforeCleanupElement`, e.g. destroy a Tom Select or remove a TinyMCE editor), swaps that replace state (`hx-preserve`), and mixing two mechanisms (use either `deform.addCallback` or `htmx.onLoad` for a widget, not both). Checked only by reading the sources (Deform's `deform.js` and htmx 2.0.11): there is no browser test yet. Server-side tests can assert that fragments carry the right markers; real behaviour needs a browser test (Playwright or similar).
- **Configuration.** Structure is RDF, validated by model shapes (content types, shapes, views, grants, anything others refer to), and edited with generated forms. Extension-private leaf settings are JSON: stored as an `rdf:JSON` literal on a plugin-settings resource (verified: datatype and value survive `put` and `get`), validated by a Colander schema the plugin registers, edited with Deform (a plugin may bring its own widgets), with a settings version for migrations. Planned directive: `config.add_plugin_settings(name, schema, scope, version)`, with an edit view per plugin under the repository. Secrets must not be echoed back. Build the JSON mechanism when a plugin needs it, not before.
- **OpenAPI from shapes.** Cornice with Colander schemas and `cornice_swagger` did this (cornice 6.1.0, 2024-02; cornice_swagger 1.0.1, 2022-06, producing Swagger 2.0; the Colander to JSON Schema converter `colander-jsonschema` 0.2 is from 2014): all stale. Since the shape is the source, derive JSON Schema (OpenAPI 3) for the compact JSON representation straight from the shapes and put it in the per-caller `/<repo>/api` document. RDF bodies are described by media type only.

## Extension levels

What an extension can be, from data only to code. The rule: whatever can be said with shapes, stylesheets and parameters is data; code is for new behaviour.

1. **Content type package.** (Superseded for shapes and stylesheets by "Types are packages": they are files in a package, not data.) The class, its SHACL shapes, form hints (`sh:name`, `sh:order`, later `sh:group`), views (XSLT stylesheets with checksums and parameters) and grants. It lives in the repository's graph, is installed and changed at runtime, and is validated by the model shapes. The form and the validation are generated from the shapes. An update is accepted only if the existing resources still validate against the new shapes (the old plan's update policy). No code and no deploy. Authors are repository administrators (`contenttype:manage`); stylesheets are trusted presentation code, and in-process Saxon has no sandbox (open question).
2. **Plugin settings (data plus a schema).** JSON settings as an `rdf:JSON` literal, validated and edited through a Colander schema and Deform form that the plugin registers.
3. **Code plugin (a Python add-on).** An installed package, included at startup with `config.include`: custom API endpoints and views, custom permissions, widgets and validators, a security policy, new directives. It needs a deploy or restart and is installed by the operator only, never uploaded by a tenant. Its operations use the same permission names and are described with `add_api_operation`, so they appear in `/<repo-id>/api` only for callers allowed to use them.

## Processes and the single-writer limit

DuckDB lets one process hold a file read-write, and that process blocks every other process, read-only ones included (tested). Read-only holders can share a file. DuckDB 2.0 has the **Quack** protocol: one owner process runs `CALL quack_serve('quack:localhost:PORT', token = ...)`, and other processes `ATTACH` to it and `CONNECT`, which routes their SQL (reads, macros, transactions, writes) to the owner.

```
gracia serve-db    the owner: initialises the schema, runs quack_serve, shuts down cleanly
      ^            (the plain `duckdb -serve` binary might do, untested)
      | Quack, localhost, token
      |-- web workers (the WSGI app under gunicorn or waitress, each process with a small pool of Quack connections)
      `-- admin CLI (`gracia ...`: attaches over Quack when an owner runs, opens the file directly when none does)
```

- **Separate by design.** The owner outlives web deploys; the web app and the owner restart independently. In production a process manager (systemd, compose) runs two services. For development `gracia serve` starts both in one process group and stops them together; it is not a supervisor.
- **One setting** (`gracia.db`, in `config.ini`, `$GRACIA_DB` or `-d`) tells the app where the database is: a file path (this process owns the file; one worker; the simplest start) or `quack:host:port` plus a token. Moving between them needs no code change.
- **Recycling workers** is the server's job: gunicorn has `--max-requests` with `--max-requests-jitter` (waitress has no recycling, and running several processes under gunicorn with the Pyramid app is untested). Only add it after measuring memory growth over a long run. In-process DuckDB means a single process, so a recycle closes and reopens the file; do not use `--preload`. With a separate owner, workers are stateless and recycle freely. Keep long jobs out of web workers.

What Quack mode requires (found by testing, localhost, small scenarios):

- **Built (what the code does now).** `config.ini` (`[app:main]`, `gracia/config.py`; the file is `-c`, else `$GRACIA_CONFIG`, else `config.ini` in the current directory when there is one, so every command, `serve-db` and `serve` included, is driven from it without `-c`; `$GRACIA_CONFIG` set to nothing means no file (the tests do that, in `tests/conftest.py`, so that the `config.ini` of the project is never read by them); a file that is named and missing is an error, the default one that is missing is just no file; a job's process is started with the absolute path of the file in use, so that it reads the same one wherever it runs; within the settings: flag > environment > file > default) holds `gracia.db` (a file, or `quack:host:port`), `gracia.db.file` (what `serve-db` opens), `gracia.db.token_file` (or an inline `gracia.db.token`) and `gracia.base_iri`. With a `quack:` target `Application` makes **one attachment per `Store`** and `Store` runs every statement on the owner through `quack_query_by_name` (`remote.py`, `RemoteConnection`); only the staging appender and its temp table stay local. A pool of those attachments, reconnecting and retrying on connection errors are not built (an attachment is made per store).
- **Finding the owner without a config.** `serve-db` writes two files next to the database: `<db>.token` (the secret, 0600) and, while it runs, `<db>.owner` (its address and token file; removed on a clean stop, left behind by a crash). Commands on a file database look for `<db>.owner` (else the default port, if a `<db>.token` exists), connect to confirm, and use the owner; otherwise they open the file, and a lock error then says why discovery failed. `serve-db` never writes `config.ini`: that file is the operator's. A `-c` file or a `quack:` target always wins.
- **Remote is not transparent, and the differences are why `tests/test_remote.py` runs the application operations against a real in-memory owner.** Found by testing: (1) all cursors of one attachment share one session on the owner, so two stores overwrite each other's current schema and interrupt each other's queries: hence one attachment per store; (2) `USE schema` is not applied to unqualified DDL on an attached catalog (tables silently landed in the owner's `main`): the owner session gets its own `USE`; (3) an `INSERT ... SELECT` that reads and writes the remote is planned locally with the wrong defaults (the `nextval` default fails); (4) several streaming scans in one query are refused; (5) the local view of the remote catalog goes stale after DDL (`quack_clear_cache()`); (6) appenders and temp tables are local only: staging is a regular table on the owner, filled by `INSERT ... SELECT` from a local temp table. Any new `Store` feature needs a case in `test_remote.py`.
- **Concurrent writers retry** (also in-process, not only over Quack): two loads adding the same new uri collide on the dictionary's unique key at commit; `Store.load` repeats the transaction (`LOAD_ATTEMPTS`, jittered pause). The load flattens the staged rows and runs the hooks *before* it touches anything another writer touches (the transaction counter, the id counters), so that two writers are in each other's way only for the writes; and it tries `LOAD_ATTEMPTS = 20` times, not 8: with the counter row of the history in every write, a test with three threads of writers on a machine busy with sixteen such tests ran out of 8 (11 of 16 failed), and passes with 20 (32 of 32).
- **A pool of attached connections.** A cursor made from a `CONNECT`ed connection does not see the server's tables. One `ATTACH` + `CONNECT` per pool slot works (an explicit queue pool; SQLAlchemy's default pool failed under threads).
- **No client-side Python helpers.** Bound parameters in `executemany` and the Python appender do not forward. Use literals, and move bulk rows with a local staging table and one `INSERT INTO qk.main.t SELECT * FROM local_table` (400,000 rows in 0.08 s).
- **Retry writes** on a transaction conflict and on the dictionary's unique-key error: two sessions replacing the same resource always ended consistent (one writer's rows, never a mix), but with conflicts and one unique violation at commit. The Python write lock does not cover other processes.
- **Reconnect on connection errors.** After the owner restarts, existing connections stay dead ("Invalid connection id"); a fresh attach works at once. A transaction in flight is lost.
- **The token is a master key:** full SQL access to everything the server sees, all repositories and password hashes included. Localhost only, token in an owner-only (0600) file or the environment, never behind a reverse proxy.
- **Quack is new.** Not tested: a client and server on different DuckDB versions, a changed token, backups taken while the owner runs (do not copy the file under a live owner; use an export).

## Changes to a record: history, slugs and the save path (mostly built)

**The rule.** The database enforces what must hold for every writer, including a stray edit in the DuckDB CLI: that is **history**, and nothing else. Policy (slugs, validation, derived values, defaults, process of uploads) is application logic, where it can grow and be tested. History makes that safe: everything derived can be rebuilt from it, so a raw write that bypasses the application logic is a drift that a command can find and repair, not a loss.

**What DuckDB 2.0 triggers can do** (tested on 2.0.0; docs: `duckdb.org/docs/2.0/sql/statements/create_trigger`). `AFTER INSERT | UPDATE | DELETE ... FOR EACH STATEMENT`, with `REFERENCING NEW TABLE | OLD TABLE`, one statement as the body, several triggers on one event if all are statement-level. Not supported: `BEFORE ... FOR EACH ROW`, `UPDATE ... FOR EACH ROW`, `INSTEAD OF`, temporary triggers, **`MERGE INTO` on a table with triggers**, no `DISABLE TRIGGER`. A trigger cannot write to the table it watches ("Recursive trigger chains are not yet supported"), so nothing can be written back into `triples`, and `gracia:modified` cannot be a stored triple. A trigger cannot write to a temp table (another catalog, and temp tables belong to one connection). Two statement-level triggers on the same table and event that both read the transition table crash 2.0.0 (`INTERNAL Error`) when they are delete triggers with aggregating bodies: use one trigger per event. `at` is a reserved word (the column is `recorded_at`).

**History** (the one thing the database guarantees). One table per repository, one row per record per transaction, kept by an `AFTER INSERT`, an `AFTER UPDATE` and an `AFTER DELETE` trigger on `triples` (one delete trigger, which writes either the snapshot of what is left or a tombstone):

```
history(s VARCHAR, recorded_at TIMESTAMP (UTC, the transaction's time), op VARCHAR ('put' | 'delete'),
        doc STRUCT(loc VARCHAR[], p VARCHAR, o VARCHAR, lit VARCHAR, lang VARCHAR, dt VARCHAR)[],
        PRIMARY KEY (s, recorded_at))
```

`doc` is all the rows of the record after the change (empty for a delete); the insert is an upsert on `(s, recorded_at)`, so the delete and the insert of a replace-save (one transaction, one time) leave **one `put` row**; a partial delete leaves a `put` with what is left; a full delete a tombstone. Tested: one save costs 17 ms with 100,000 records and about 60 ms from 1,000,000 on (a scan of `triples` per statement; neither a sort nor an index helps; a set-based statement pays once), 2 ms without the triggers. `gracia:modified` is the latest `recorded_at` of the record, read from `history` and added when the triples are read (`triples_rows`, the exports, perhaps a view); it is not stored in `triples`. The history is exported by a daily job or cron (`gracia history export`): a `COPY` of the day's rows (those with `recorded_at` inside the day) `TO 'history/<repo>/<day>.parquet'` (the nested `doc` round-trips through Parquet and JSON Lines; DuckDB's `COPY ... (APPEND)` does not append to a file, it replaces it, so one file per day, written again if needed). Consequences for the rest: `merge.sql` and `delete_resource.sql` become delete then insert in one transaction (no `MERGE`); `Store.sort()` drops and recreates the triggers inside its transaction (or it would snapshot every record). The history keeps everything. Later it gets more columns: where the edit came from (job, editor, API) and by whom, which the trigger cannot know, so it needs a way in from the save path below (a connection variable, or the `Store` setting it).

**The `records` table (built; the first triggers).** One row per record (a subject `rec:<type>:<n>`; other subjects have none), per repository next to `triples` (`assets/sql/records.sql`, the macro `record_rows` in `macros.sql`): `rec_uri` (primary key), `rec_type`, `rec_number`, `res_uri` (`gracia:resource_uri`), `created_at` and `modified_at` (UTC: the values of the properties `gracia:created_at` and `gracia:modified_at`, which their predicates make, so the column and the property are one value; a record written without them gets the time of the transaction, and for `created_at` the time of its first history row), `is_published` (`gracia:is_published`, true when there is none), `label` (`gracia:label`), `identifiers` (the values of the properties with `dash:KeyInfoRole`), `"references"` (every object uri of the record's rows, bnodes below it included; quoted, it is a reserved word), `text` (the literals of the properties with `dash:DescriptionRole`, joined by newlines), `source` (the record as N-Triples: literals are JSON strings, uris are JSON strings with `<` `>` written `&lt;` `&gt;`, blank nodes are uuids, new on every rewrite). An `AFTER INSERT`, `AFTER UPDATE` and `AFTER DELETE` statement-level trigger set on `triples` (`<triples>_records_<event>_<n>`, now 15 triggers an event (eight when this was written), which fire in the order of their names: delete the list rows, the unique values and the record row of the changed records, then insert them again, plain `DELETE` and `INSERT` since `ON CONFLICT DO UPDATE` is a merge and cost ten times as much, measured) rewrites the whole row of every record whose rows were in the transition table (an empty one is an empty list, not NULL: NULL would mean every record); a record left without rows has no row (it is in the history, as deleted; `records` holds the live records only, so nothing reads `is_deleted` from it), and a replace-save (delete then insert, one transaction) leaves a live row. Consequences: `merge.sql` is a `DELETE` of the staged subjects followed by `insert.sql` (no `MERGE`, so the counts are the rows deleted and inserted); `triples_rows` has a last column `root` (the record of the row); `record_rows` uses `triples_rows`, and DuckDB will not replace a macro that another macro uses, so `Store` drops the triggers and `macros.sql` drops `record_rows` before the macros are made again; `Store.sort()` drops and remakes the triggers in its transaction. `identifiers` and `"references"` have list tables (`records_identifiers`, `records_references`, kept by the same triggers; `Store.records_with`). They have no index, and neither does `slugs` beyond its key: an index makes the commit of every large write slower, and the commit holds up the commits of every repository (2.8 s against 1.2 s for 300,000 records); the scans cost 1 to 5 ms at that size. The `etags` table is made from `records` and `records_references` (see the section on etags). Full-text search is not built: DuckDB's `fts` index is a snapshot that has to be rebuilt whole (and the community `tantivy` extension indexes the table in RAM on every call), which does not fit PDF text; the plan is tantivy-py with its own index directory, fed from a change log table written by the triggers (`records_changes`, not built) by one indexer; `text` stays a plain column until then. `Store.get` reads records from `source` (their N-Triples, parsed together) instead of rebuilding them from `triples`.

**Unique values (built).** `unique_values(rec_type, p, value, s)` has `UNIQUE (rec_type, p, value)` and is kept by the same triggers from the rows of `triples` whose property is listed with the role `unique` in `property_roles` (the shapes' `dash:uniqueValueForClass`, for the type whose class it names: `gracia:userid` of a user). A second record with the value makes the statement, and so the transaction, fail with DuckDB's unique-key error, whoever wrote it, and two writers at once cannot both commit; saving the same record again, changing the value and deleting the record work (tested; the first and last were the worry, since a delete and an insert of one key in a transaction can be refused). `Store.load` turns the error into `DuplicateValue(rec_type, predicate, value, holder)` (the holder is looked up) and does not retry it (it retries the lost races); the forms show it as an error ("The userid 'ada' is taken (by rec:user:1)"). Marking a property unique where records already share a value changes nothing and is a `DuplicateValue` too. A soft reminder, not a refusal, is the key info role: `Store.records_with("identifiers", value)`.

**The jobs of a type (built).** The manage page of a type has a **Jobs** tab (`TypeManage.pane_jobs`, `templates/type_tab_jobs.pt`): for each of the jobs about the records of the type that the user may start, a row with a Start button that posts the fields of its own form to the jobs node (`jobs.js`, `data-start-job`), and under them the table of the jobs of this type (`subject=<slug>`) with the dialog that follows one. The jobs are `validate` (with a select of the schema files of the type, a candidate revision included), `export` (`jobs/type_jobs.py`: the `Export` stage with no chunks; the job offers the records as one N-Triples file, `export.nt`, to download: a stage can have a classmethod `offer(job_dir, stages, index)` that the runner asks when the job ends with no rejected items) and `rewrite` ("Rewrite records": the `Rewrite` stage). **Rewrite** is what a switch of the schema of a type needs, since the label and the other values the hooks make follow from the shape the records were saved under. It does not save the records again: `Store.rederive(type, numbers)` copies the rows of a batch of record numbers to `flat`, runs the SQL hooks on the copy and stores only the difference (`EXCEPT ALL` both ways, a delete of the rows that went and an insert of the new ones, one transaction), so a record the hooks leave as it is is not touched and the triggers (the records table, and the history when there is one) never see it; the records that changed are what passes on. Batches are `size` record numbers (the plan is the id counter of the type, one number). A job runs in a process of its own, so `jobs/context.py` makes the application's configuration there (once per process, `begin`/`end` around a `repository()`): without it the predicates are not registered and there are no hooks. The `records` columns that come from roles (`identifiers`, `text`) are made again by `Store.set_property_roles` when the roles change, not by this job.
**The jobs of a repository (built).** The manage page of a repository has a **Jobs** tab too (`RepositoryManage.pane_jobs`, `templates/repository_tab_jobs.pt`, the jobs in `jobs/repository_jobs.py`), the same idea one level up: a row with a Start button for each job that is about the repository as a whole and that the user may start, and under them the table of the runs of that job (`job=rebuild_etags`). The one job so far is `rebuild_etags` (stage `RebuildEtags`, no parameters): it makes the etags of every record again from the data and lists the records whose etag was wrong, so it is also a consistency check; its group list is empty, so only the administrators may start it (`Job.groups`).

**The history (built; `history.py`).** `history(rec_uri, txn_id, modified_at, is_deleted, source)` holds every record that a statement changed, as `records` has it after the statement (the columns of `records` and `is_deleted`: a deleted record has no row in `records`, so its history row, written from the subjects of the statement that have none, is a tombstone with an empty `source`), one row for a record and a transaction; the triggers on `triples` write it (two more trigger steps, 11 an event, 33 on the table before the slugs, now 15 an event and 45; they fire **in the order of their names**, so the numbers in them are zero padded: `_10` sorted before `_2` once and the references were made before the records). Storing the whole record each time, not the changed triples, keeps a restore a plain read. **The transaction number** is an increasing number kept in SQL: the counter row `_transaction` of `ids`. Every write through the store (`load`, `delete`, `rederive` when it changes something) takes the next one *inside its own transaction* (`INSERT ... ON CONFLICT DO UPDATE ... RETURNING last`) and hands it to the triggers in the session variable `txn_id` (`SET VARIABLE`, which the triggers read with `getvariable`). Because the counter row is part of the transaction a rollback gives the number back (no gaps), and a second writer conflicts on the row until the first has committed, so the numbers are in the order of the commits, which is what lets a reader keep one number and ask for `txn_id > number` (`Store.changes_since`, the rows of a transaction are together at the end of the table). **A write outside the store** (the DuckDB shell) has no variable: the first trigger of every statement then increments the counter itself, and the history rows of that statement take it, so a reader that is at n and sees `Store.last_transaction()` > n knows it is behind; it is the same counter, in the transaction of the write (a rollback gives it back, and a second raw writer gets a transaction conflict and retries). Numbers from a sequence would have holes that mean either a rollback or a write that has not committed yet, and nothing tells which. **No file.** There was a file `<repo>_last_transaction_id.txt` (and `history.TransactionWatch`, `Application.last_transaction`, `Repository.last_txn_id`, the setting `gracia.history_dir`) for caches to learn that something was written. It was removed once the etags existed: they are kept in the same transaction as the data (`Store.refresh_etags`), so nothing has to be told that something was written. Not built: the parquet files (a flush after the commit, with a daily merge), the search index that follows `changes_since`, and the removal of rows from `history`. Measured: the history costs nothing visible on a load of 5,000 records (0.8 s, the same).

**What still reads `triples`.** The reads that were about whole records go through `records` now: `Store.get` and the export (the `source` column), the records of a type and their count (`records_of_type`, `count_records_by_type`, the Types tab of the manage page), the record that a resource URI belongs to (`record_with_resource_uri`, the ARK resolver), the user a login names (`records_with("identifiers", userid, rec_type="user")`, since the userid is key info) and the numbers (above). `Store.find` and `subjects_of_type` are gone. What is left needs the rows: the values there are of each property (`count_by_predicate`, the Predicates tab), the namespaces in use (`used_prefixes`: the predicates and datatypes are not in `records`), the json-triples export (`export_json`, from `triples_rows`), and the writes (`rederive`, the unique values and the records made again when the roles change, `sort`). **The roles are in the database from the start:** `Repository.sync_roles(store)` reads the types again and tells the store what their shapes say; it is called when a repository is created, when a type record is saved (`Record.save`), by `gracia types add` and at the end of `gracia import`, so the key info of the users is there before the first login and a type that was just added has its roles before its first record.

**The numbers of a type, and reserving them (built).** The `ids` table has a column `reserved` besides `last`: `last` is the number a form or an import was given most recently, `reserved` a floor that a person sets, and the next number is past the greatest of `last`, `reserved` and the highest number of the type that a record has or had (`records` and the history). `Store.numbering(type)` gives the parts (`given`, `reserved`, `highest`, `taken` = greatest of the first and the last, `next`) and `Store.reserve_ids(type, number)` sets the floor, in a transaction, and refuses a number below `taken` (`ValueError`, a record has a number higher than that, or a form was given one): it can be set higher, to keep a swath of numbers for an import of records that come with their own, and set back to `taken` to give it up. A separate column (and not just raising `last`) means a reservation can be lowered again without ever going below a number that an open form holds. The **Identification** tab of the manage page of a type, before the Jobs tab (`TypeManage.pane_identification`, form `form-type-identification`, permission `manage`), shows the number that is taken, editable, and below it the highest record, the last number given, the reservation and the next number. The Rewrite job plans over the highest record, not over what is only reserved.

**History in the edit view (built; `views/history.py`, `templates/history.pt`, `static/scripts/history.js`).** The edit page (form and source) of a record has, above the buttons and right aligned, when the record was last changed (`views/last_modified`: "Last modified 5 minutes ago", hours, days, and after 30 days "Last modified on Monday, August 23 2026"; from `records.modified_at`, UTC), and the toggle between the form and the source is a button now, with a **History** button next to it; neither is on the add page, and a record whose source may not be shown (`source_editable`, the user: its history has the hash of the password) has no History button and answers 404. `/<repo>/<type>/<n>/history` (permission `edit`) lists the versions in the `history` table newest first, in the style of the extensions (`Store.revisions`): the number of the transaction, when (UTC) and how long ago, a *current* badge on the newest and a *deleted* one on a tombstone. **View** opens a dialog with the version in the read-only editor of the source page (Turtle, nested blank nodes, so no labels and two versions that say the same are the same text) and, on another tab, what it changed since the version before (`difflib.unified_diff` of the two Turtle texts, `?txn=<n>` answers JSON for it); **Restore** asks (`data-confirm`, `manage.js`) and posts `/restore`, which saves the version as the new current one by the same path as every save (`Record.save`, so the hooks run again and it is a version of its own; the versions after the restored one stay) and refuses a tombstone, a version that is not there, a post from another site and (as a flash) a unique value that is taken now. The diff is made on the server for want of a merge component in the vendored CodeMirror.

**The index view of a record (built, first step; `views/index.py`).** `GET /<repo>/<type>/<n>` is the page of a record. The records its page is made of are found by `Store.dependencies(record, depth)` from `records` and `records_references` (which is what the references table is for): the record, every record that one of its objects names (an object that is the *resource uri* of a record, or the uri of a record), those records' objects, and so on, `MAX_DEPTH = 10` steps out; a record is looked at once, so a cycle ends, and a deleted record is not one. One query a step, two joins each on a single column (an `OR` would not be a hash join). The **etag** used to be the md5 of the sorted lines `<record uri> <modified_at>` of those records, found at every request. It is now read from the `etags` table, made when something is written (`Store.etag_info`; see the section on etags: an XOR of hashes of the record and everything it points at, with the version of the schema files added by `page_etag`); the walk above (`Store.dependencies`, `etag_of`, now blake2b) is only the fallback for a repository that has no etags yet. It changes when the record or anything it is made of changes and not otherwise (the type record is among them, through `gracia:type`). The browser's `If-None-Match` is answered with 304 before anything is built; otherwise the `source` of those records is one graph, without the credentials, written as RDF/XML with the prefixes of the repository, nested by `rdfxml-to-nested.xsl` (the stylesheet that puts blank nodes and collections inline), which is given the uri of the record as its parameter `record_uri`: the element of the record is the first one, the others keep their order (`Graph.serialize(..., xslt_params=...)`, `xslt.nest(flat, params)`). `Cache-Control: private, no-cache`: it always asks and the etag answers. **Content negotiation:** `Accept: application/json` gets the plain values (`views.type.record_values`), `text/html` (a browser) the page `templates/record.pt` (`views.type.record_page`), anything else the RDF/XML. **The shapes are in the page:** the types of the records of the page are known from their uris (`rec:<slug>:<n>`), and the shape every record has and the shape of the content of each of those types (`Type.shacl_shape(include_record_shape=False)`, the schema file the type is on) are added to the graph, so a stylesheet can title and order properties (`sh:name`, `sh:order`), find the label and the key info (`dash:propertyRole`) and choose a language (`sh:name` with a language tag; none of the shapes has one yet). A page has the shapes of the types it is made of and not those of the others (the person shape is in the page of a book that points at persons, the user shape is not); the etag takes in the version of the files of each of those types (`Type.assets_version`, so a change of a schema file changes the pages that have its type), and the prefixes `sh` and `dash` are declared. Measured on a page with three persons: 12.7 KB, 49 ms for the whole request, of which a 304 is 39 ms (the rest is the request itself: traversal, the types of the repository, the closure). Not done yet: look up a rendered file by the etag, a page made by the XSLT of the type, the permissions of the linked records (a record the caller may not see is still in the graph), and a limit on the number of records.

**Back-references on a page (built in part; the rest is design).** A person's page lists the person's articles: the records that point at this one, a page at a time. *Built* (see "Etags, batches and the pages of a listing"): `Store.referrers` pages through the `etags` table, with both totals read from the row of the record (`backref_totals`), and the etags are kept by the writes. The first design computed the etag of such a page at every request ("pull, not push"), with an index on `records_references`, a SQLite fragment cache and a memo on a last-transaction number in front of it; the writes now do that work, and none of those was built (the indexes and the last-transaction file are gone). *Still design only:* the set of a page declared by the view of the type as rules (the forward depth from the record, the back-references of one type, one hop and never followed on, a page size and an order, and for each listed record a small forward depth: its title, its journal); a generated resource in the graph for the listing (its page, size, total and an rdf:List of the records in order, so that the stylesheet lists them without sorting) with the same things in the etag; leaving out of the listing the records that the caller may not see (the open point about permissions); and a predicate column on the references, since "articles of this person as author, not as editor" cannot be said without one (the `etags` table has none either). **Where to page (measured, not decided).** With Saxon (a document of N articles, rendering page 2 of 20 sorted by date) parsing costs about 7.5 ms per 1,000 articles (0.4 MB), and sorting, slicing and rendering 20 another 2 ms at 1,000, 29 ms at 10,000 and 111 ms at 50,000 (parse 75 ms and 365 ms there): paging in the stylesheet is free for the hundreds that a person has and too slow for the tens of thousands that a journal has, so page in the stylesheet below a threshold of items (the totals are in the row), and in the query above it (`Store.referrers`). **Decision for now: no cache of fragments.** `records.source` already is the per-record fragment (N-Triples, read by key): `Store.get` concatenates the sources of the records of a page and `Graph.serialize` writes and nests them as RDF/XML (about 2 ms and 6 ms for 33 records). A cache of fragments keyed by (uri, `modified_at`) in a SQLite file was measured (33 fragments by key 0.11 ms against 5.8 ms to serialize and nest them) and is the alternative if that is ever not enough: fragments, not bundles of a record with its closure (a bundle is 19 KB where a fragment is 0.6 KB, and a change to a person would rebuild every bundle it is in).

**Slugs (built).** `slugs(rec_type, slug, record_uri, is_deleted)`, primary key `(rec_type, slug)`, never loses a row; `records.slug` is the current one. `gracia:slug` is a top-level property of a record (`model/record.shacl.ttl`, order 2.5, pattern `^[a-z0-9]+(-[a-z0-9]+)*$`) with its own predicate (`predicates/gracia_slug.py`): the form field is a text input with a `<datalist id="slug-options">` of the record's old slugs (`Store.slugs_of`). Its write hook (four SQL statements on `flat`, idempotent) takes the slug that is stated, else makes one of the label (`slugify` macro: accents stripped, lowercase `a-z0-9` and dashes, other characters removed, at most 80 characters, not all digits, not `add` or `manage`), and makes it free: a slug that another record has, deleted records' included, becomes `john-doe-2`, the next free number (gaps are filled), records of one batch are numbered in the order of their numbers; a record may keep or take back one of its own old slugs. A record that already has a slug keeps it when its label changes. Four trigger steps on `triples` (15 an event, 45 on the table) keep `slugs` from `records.slug`: insert the new slug, and when a record is deleted its numeric id is inserted as a slug with `is_deleted` true (and its slugs are marked deleted). `Type.__getitem__`: a number finds the record or answers `410` if it once existed (history/slugs) else `404`; a slug is looked up in `slugs` (`Store.slug_lookup`): the current slug is the record, an old one answers `301` (`308` for a method that is not GET/HEAD) to the current slug, or the number when there is none, keeping the rest of the path and the query; a slug of a deleted record is `410`; an unknown one `404`. A record's address is its slug when it has one (`Record.__name__`, so `request.resource_url(record)` and the redirects after a save use it), else its number; the number of a record that has a slug answers `301`/`308` to the slug (`Type.by_number` is the lookup without the redirect, for the ARK resolver and the type listing). The slug field is a text input with a drop-down of the previous slugs (the current one marked); choosing one fills the field, and saving uses it again. **Purge** is a job of the type (Jobs tab, `purge_slugs`, stage `PurgeSlugs`, `Store.purge_slugs`): it deletes the slugs of the live records of the type that are not the current one (those addresses answer 404 afterwards); the current slugs and every slug of a deleted record, with its numeric tombstone, stay. Tests: `tests/test_slugs.py`. Writes outside the application are not renumbered (the hook is not run).

**The one save path (built as `Record.save`; what is left).** Every save of a record goes through `Record.save(store)`: the forms, the type and repository settings, and an import (`gracia import`). What it runs are the **write hooks** of the predicates, which are SQL on the batch that is stored (`Predicate.on_write_sql`, see "Predicates and the shape of a record"), not Pyramid events: events broadcast and return nothing. Left for later, when something needs it: (1) an event **after** the write (`RecordSaved`: process an uploaded PDF, update the full-text index, anything that must not delay or break the save; Pyramid's `registry.notify` and `config.add_subscriber` fit that); (2) the **previous version** of the record in the hook (hooks that react to a change, such as regenerating a slug when the title changes; SQL can read `triples` for it); (3) a way to **refuse** a save with a message per field (the unique values are the first refusal: `DuplicateValue`); (4) where the `source` and `by` columns of the history get their values; (5) jobs and the CLI get the same registry through `cli._repository`, which builds it the way the web application does.

**Slugs are the test case for the save events.** The slug extension is the first real subscriber, and it needs the hard parts, so the design of the events is derived from it, and it is built with them: (1) a hook **before the write** that may change what is written (the number of a taken slug goes into the `gracia:slug` triple before the insert); (2) it **reads the database inside the save**, in the same transaction (`slugs`, to see what is taken); (3) it must work for a **bulk save**: numbering is set-based per family over the whole batch, so the event cannot only be one record at a time (a batch event, or one event that carries all the records of the save); (4) a **refusal channel**: a typed slug that collides is an error that reaches the form like any other validation error (`ExtensionError`-like, with a message per field), and a refused save writes nothing; (5) **races**: two saves taking the same number fail on the primary key of `slugs` and the save is repeated, so the hook must be safe to run again; (6) it only runs where the **extension is enabled** (`repo.extension("slugs").enabled`); (7) an **after the write** hook (`RecordSaved`) for what must not break the save, such as the redirect table or later the PID and the full-text index; (8) it can be **rebuilt from the history**, so a write that went around it is a drift that `gracia slugs rebuild` repairs. If the events carry all of that for slugs, they carry what a PID extension or an upload processor needs.

**Predicates and the shape of a record (built).** The form of a record is made from **SHACL**: the record shape (`model/record.shacl.ttl`: `gracia:type`, `gracia:resource_uri`, `gracia:label`, `gracia:slug`, `gracia:resource`, `gracia:is_published`, `gracia:created_at` and `gracia:modified_at`, in `sh:order`) with the shape of the type's content embedded on `gracia:resource` with `sh:node` (`Type.shacl_shape()`, `assets.record_shape`). `Record.edit_schema` makes one Colander node per property, recursively (`forms.properties`, `forms.leaf_node`, `forms.nested_shape`; a property whose value is a URI or a blank node gets a field only from a predicate), so the shape decides which fields there are and in which order. **A predicate is the code for one property, registered under its URI** (`gracia/predicates/`, a package like `gracia/extensions/`: `__init__.py` is the contract, `IPredicate`, and **each predicate is a module of its own named for it**: `gracia_resource`, `gracia_resource_uri`, `gracia_label`, `gracia_schema` with its `SchemaWidget`, whose template is `templates/schema_validate.pt`; tests in `tests/test_predicates.py`). It is a class marked `@predicate(uri.LABEL)`, found by `config.scan` (or `config.add_gracia_predicate(cls)`; two for one property are a conflict, and the application's replaces one that comes with gracia), with parts that are all optional: `schema_node(record, request, schema_node)` (given the Colander node the shape made, returns what the form should have, or None) and `on_write_sql(context)` (the write hook, below). A property with no predicate is a plain text field that is stored as it is. **The write hooks are SQL.** A hook returns the statements (strings) that run on the rows of the batch that is being stored, between flattening them and inserting them: `Store.load` flattens the staged rows into the table `@FLAT@` (the columns of `triples`), runs the SQL of every predicate of every type on it (`Type.sql_hooks`: what is embedded first, then the record's own properties, in `sh:order`; the repository hands the store its types, `Store.configure(lambda: repository.types.values())`, and the store reads their `sql_hooks`, `property_roles` and `number`), deletes the old rows of the records and inserts `flat`, all in one transaction. A hook sees all the records of the batch at once, so it works on sets, not on records; it has to give the same answer when it is run twice, and it leaves other types alone (`HookContext.of_type`). The SQL is Python code (tested with literal rows in `tests/test_labels.py` and `tests/test_predicates.py`), and what a form edits is only what it is made from: the hints in the shapes. Every save is the same path: `Record.save` `store.put`s (the store of a repository is configured when it is opened or given, `Repository.configure`); `gracia import` does the same; `Store.apply_hooks(graph)` runs the hooks on a graph and gives it back without storing anything (the source view uses it to check a text as it would be stored; `Repository.with_hooks`). A store that is not configured (a plain triple store) runs no hooks. **Hints in the shapes** (`hints.py`): a property shape can say `dash:propertyRole dash:LabelRole` (the values of such properties, in `sh:order`, make `gracia:label`), `dash:KeyInfoRole` (they make `records.identifiers`), `dash:DescriptionRole` (`records.text`), and `dash:uniqueValueForClass <class>` (no two records of the class have the same value). These are the DASH vocabulary (http://datashapes.org/dash), annotations that SHACL validators ignore; rudof does not enforce `dash:uniqueValueForClass` (tested), and a validator sees one batch, never the other records, so the database enforces it (`unique_values`, below). The SHACL roles of the types go to the store (`Type.property_roles`, read by `Store.set_property_roles`; the store compares them with `property_roles` before a load and, when they changed, makes the records again). Five predicates were the first (more came, see the next paragraph): `gracia:resource` (adds the fields of the record class that are not stored as they are, such as the password, to the content mapping), `gracia:resource_uri` (**all of its code is in `predicates/gracia_resource_uri.py`**: the field, and the ARK from the settings of the `ark` extension as the default when a record has none; the extension itself only has the settings and the resolver), `gracia:schemaTemplate` (for the content of a type and of the repository: the field is a select of the files of the directory that `gracia:assets` names, a name that is not a file is refused, what is stored now stays a choice, and on a type a Validate button; `assets.schemas_of` is the one place that knows the files, and the validate job's select uses it too), `gracia:label` (a **read-only** field, `forms.ReadOnlyWidget`: not edited; made by its SQL from the label roles of the type: the values in `sh:order` joined by a space, of a property with several the shallowest, then the first alphabetically; no value, no label, and a form calls the record "(Unnamed)"; `Record.title`, `Record.label`), and **`gracia:propertyTemplate`**, which is not a predicate but a hint in a property shape (`templates.py`): `gracia:propertyTemplate ( "{} {}" schema:givenName schema:familyName )` on `schema:name` (and `foaf:name`) says that the property is made of the others: the text with each `{}` replaced by the value of the next property of the list, then trimmed; `[ ... ]` is an optional part, left out when one of the `{}` in it has no value (`"{} [{} ]{}"`); `{{ }} [[ ]]` are the characters themselves. The properties are those of the same node (so it works in blank nodes too) and have one plain value each (checked when the shape is read: `templates.of_shape`, `forms.single_literal`; a property made by a template is not a source of another). The property is **always replaced** when every `{}` outside the brackets has a value that is not empty, and otherwise left alone, so a name that is typed stays when a part is missing. It compiles to two SQL statements (`PropertyTemplate.sql`: delete the old value of the nodes that have all, insert the new) that `Type._sql_plan` puts before the predicates of the shape, and the shape of the content is done before the record shape, so the label (the name has the label role) is made of the new value. The form: the field is not required when the sources are (`forms.made_of`, `forms.template_validator`: "Give a name, or fill in given name and family name"), and has the template in `data-template`, which `static/scripts/template.js` follows to fill the field in as its sources are typed (`PropertyTemplate.render` is the same in Python; `tests/test_property_template.py` has the SQL and the Python agree). `schema:name` and `foaf:name` have no predicate module any more. **A template for each kind:** a template can be on a property inside an alternative of an `sh:or` of the node shape, `sh:or ( [ sh:property [ sh:path schema:propertyID ; sh:hasValue "ORCID" ] ; sh:property [ sh:path schema:url ; sh:pattern "^https://orcid\\.org/" ; gracia:propertyTemplate ( "https://orcid.org/{}" schema:value ) ] ] ... )`: it is for the nodes that have that alternative (its one `sh:hasValue` says which), the shape checks the rest of the alternative as it checks any (so the URL has to start so), and the form uses the same alternative (below). The SQL has a statement for each, the browser gets all in `data-template` and takes the one that fits when the select changes; what a template made is taken away again when the value changes to one that has none. A target with `sh:nodeKind sh:IRI` gets an IRI, not a literal (and only when the text can be one). An IRI property is a text field only with `dash:editor dash:URIEditor` (until there is a widget for it); `sh:in` is a select. **Rules of the alternatives** (`forms.alternatives_validator`): the form does not run the shapes, so an `sh:or` of a node shape whose alternatives are only `sh:hasValue`/`sh:in` (which kind) and `sh:pattern` with its `sh:message` is also a validator of the form, with the message at the field (PropertyValue: the kinds of identifier and the form of each value); the shape itself checks them too, for imports and the source editor. **Several plain values** (`forms.BagWidget`, `bag.pt`, `bag_item.pt`): a property with no `sh:maxCount 1` and no `sh:node` whose values are literals (the shape gives a `sh:datatype`, or allows a language) or IRIs typed as text (`dash:URIEditor`) is a list of rows, at least one (so it looks like the field of a property with one value), the last with a `+` at its end that adds a row and the others with an `x` that takes them away (`forms.is_bag`, `forms.bag_node`; the buttons are htmx like those of the blank nodes, `change_sequence` serves both, the row that was added is marked `data-autofocus` and `static/scripts/form.js` focuses it, `sh:minCount` and `sh:maxCount` are the limits and rows with nothing do not count). `form.js` also makes a pressed submit button busy (disabled, its icon a spinner); the caret of a `LanguageWidget` is out of the tab order (the arrow down in the code input opens the menu). **The bars of the nodes** have no chevron: a bar lights up under the mouse (not when the mouse is on its x), takes the tab key and shows a ring inside it when it has the focus; Space and Enter open it (the browser's `<details>`, which shuts the others), the arrow keys go to the next or the previous bar, Delete takes the node away, and its x, an addon of the bar (a cell over its end, with its own focus ring), is a button next to the `<details>` and not in the `<summary>`, where a screen reader may not find a button (so the tab key goes bar, x for a shut node and bar, fields, x for an open one; the bar has a fixed height, `--bar-height`, for the x to match, and Bootstrap's `z-index` for a bar that is hovered or focused would cover the x, so the x has a higher one). **Accessibility (a first step, not an audit):** every control has a name (the rows of a list are named by the list and their place, the language code by its field; `forms.labelled`), the lists of values and of nodes are `role="group"` labelled by their label, a field that is wrong has `aria-invalid` and `aria-describedby` its message (deform's `textinput.pt`, `textarea.pt` and `select.pt` are overridden for that), the icons are `aria-hidden`, and the tabs and their panels name each other (`tests/test_aria.py`). Not done: a live region for what the buttons change, a summary of the errors that takes the focus, the contrast of the light borders and icons (WCAG 1.4.11; the colours come from Bootstrap's variables, `--bs-border-color` first, and a few of ours in `gracia.css`). **Times, the published flag and the time zone (built).** Everything in the database is UTC. Four more predicates: `gracia:created_at` and `gracia:modified_at` (`xsd:dateTime`, UTC; read-only fields that show the time in the zone of the repository and are not posted, because the input has no name: `predicates/gracia_created_at.py`, `gracia_modified_at.py`, a `LocalTimeWidget` on `forms.ReadOnlyWidget`), `gracia:is_published` (`xsd:boolean`, a checkbox; true when nobody says, which is temporary, it is to be computed: `predicates/gracia_is_published.py`) and `gracia:timezone` (a property of the content of the repository record, a drop-down of the common IANA names by region with an empty choice that means UTC: `predicates/gracia_timezone.py` (the zones and `show` are in it too), `Repository.timezone()`). The three of a record are in the record shape. **The write hook of `modified_at` makes both times** (one idempotent SQL statement): a stored record whose rows changed gets the time of the transaction (`now()` is the same in every statement of one), and one whose rows did not change keeps its times (the rows are compared with the stored ones, `created_at` and `modified_at` apart), so loading the same data again, or `rederive`, is no modification; `created_at` is the stored one; a record that is new keeps the times its text has (an import or a restore keeps its dates), else the time of the transaction. `records.created_at`, `modified_at` and `is_published` are those values (`record_rows` reads the properties). `is_published`'s hook leaves exactly one `xsd:boolean` on every record. The settings form of the repository passes its fields through the predicates (`RepositoryManage._settings_form`), which is how the time zone gets its drop-down; `hints.names(shapes, shape)` gives the `sh:name` of every property, for the pages that label values (`record.pt`). Tests: `tests/test_timestamps.py`.

**How the `gracia:` predicates would function.** *Built:* `gracia:resource`, `gracia:resource_uri`, `gracia:schemaTemplate`, `gracia:label`, `foaf:name`, `gracia:slug`, `gracia:created_at`, `gracia:modified_at`, `gracia:is_published` and `gracia:timezone` (above). *Next, record scope:* `gracia:type` (structural: set when the record is made, `Record.begin`, never edited, no field). *Next, content scope:* `gracia:credentials` (the field is the password, from which the salted hash is made, never exported: today `UserRecord.extra_fields` and `apply`), `gracia:memberOf` (a multi-select of the groups, permission `manage`), `gracia:userid` (unique among users: `dash:uniqueValueForClass`, enforced by `unique_values`; built), `gracia:types` (the list of type records of the repository: `add_content_type` becomes the code of this predicate, and the slug of a new type is checked for being free), the `gracia:slug` of a type (the slug convention and the reserved words, today `init.type_turtle`), `gracia:assets` (checked together with `gracia:schemaTemplate`: the spec must resolve), `gracia:extension` (enabling, disabling and settings of an extension would be saves of the repository record whose handler enforces `can_disable`). *No code needed:* `gracia:name`, `gracia:class` (plain fields from the shape). *Derived, not stored:* nothing now: the times are stored (`gracia:modified_at`). The SQL write hook is the way each of these would be saved.

**Predicate handlers on save (an idea under discussion; its first, simple version is built as the SQL write hook `on_write_sql(context)` above: a registry lookup by property URI, called for every property of the record's shape, always, with no previous version, set-based per batch; what follows is the larger idea).** Every `gracia:` predicate may have functionality that has to run when it is inserted, changed or deleted, so instead of one generic event system the save path could keep a registry of **predicate handlers** (ZCA utilities by predicate URI, `@predicate_handler("gracia:slug")` found by `config.scan`, optionally naming the extension they belong to and only run where it is enabled). The save path works out which registered predicates changed between `previous` and the new version and calls only those handlers, with a **batch** of changes (what set-based code such as the slug numbering needs). Because only the few registered `gracia:` predicates are compared, the comparison can be done in SQL over a whole batch (staged rows joined to `triples` for those predicates), so a bulk import does not pay a Python comparison per record. A handler is the one home of everything about its predicate, every part optional: the **form field** (a Colander node with its own widget, put on the Record tab by `Record.edit_schema()`, which would ask the handlers for their nodes instead of hard-coding `resource_uri`), the save logic (before and after the write, only when that predicate changed: an unchanged slug is not looked up), the name resolution at traversal, and small helper views (a deform view for an "is this slug free" button). Examples: `gracia:slug` (the numbering, the redirects, a text input with a `<datalist>` of the slugs the record had, so an old slug can be restored, and a live check), `gracia:resource_uri` (the ARK default), `gracia:extension` on the repository resource (enabling, disabling and saving settings would become saves of the repository resource, and "ARK cannot be disabled" would be enforced in its handler for the UI, the JSON import and the command line alike), `gracia:schemaTemplate` (with `gracia:assets`, which it is checked together with: the field is the select of the schema files, the validation is that the file is in the list and loads, the dependent select and its deform view live here and the form of the validate job reuses them instead of its own copy, and after a change it says the version of the type changed and suggests the validate job; it appears at two levels, top-level on the repository resource and inside the content of a type record, so a handler needs a scope, the rdf class that carries the predicate, and may have to cover a group of predicates), and perhaps `gracia:resource` (the content: checking it against the shape of the type when it is saved, which is a large decision because that is what the validate job does today). Open: ordering between handlers, how a handler refuses a save (a message per field), the context (`source`, `by`) it gets, whether general events stay for what is not about one predicate (indexing, processing an upload after the save), and the interface itself, which should be extracted from the first three handlers (slug, `gracia:extension`, `resource_uri`) and not designed from one.

## Etags, batches and the pages of a listing (built)

What a page of a record is made of, kept ready when something is written, so that a request reads one row. Code: `store.py` (`refresh_etags`, `referrers`, `records_page`), `assets/sql/etags.sql`, `views/index.py`, `views/type.py`; tests `tests/test_etags.py`, `tests/test_html_pages.py`; the measurements are the throwaway scripts in `bench/` (nothing in `src/` uses them).

- **The `etags` table** (per repository, derived data: `gracia etags rebuild` or the job `rebuild_etags` of the repository's Jobs tab make all of it again from `records` and `records_references`). One row per record: `record_id`, `record_uri`, `record_type`, `res_uri`, `sort_key`, `is_published`, `etag`, `local_hash`, `modified_at`, `last_modified_at`, `references` (ids of the records it points at, directly), `deep_references` (the ids reached by following those), `deep_types`, `backref_totals` (below) and `state`. No index on it: a write that recomputes many etags deletes and inserts that many rows, and with an ART index the *commit* of that (5.6 s of a 9.4 s write at 1M records) held up the commits of every other repository; a lookup by id is a scan of one integer column, 0.5 ms at 1M.
- **Ids.** `(type number + 100) * 10^9 + record number`, the number of a type being that of its type record (`rec:type:<n>`), pushed into `type_ids` by the repository (`Store.set_type_ids`; changing them makes all etags again). Python makes the same id (`uri.record_id`). Stateless, never changes (numbers are not used twice), record numbers must stay below 10^9. A hashed id was considered and not chosen (collision handling; our ids have no entropy in the bits a Bloom filter would slice).
- **The etag** is `bit_xor(hash(record_id, modified_at))` over the record and everything it points at (the closure, a set: each record counts once, there is no order, cycles and shared dependencies are fine), as an unsigned 64 bit integer, shown as 16 hex digits. The etag of a page adds the versions of the schema files of the types on it (`views.index.page_etag`, blake2b). `local_hash` is the record's own part, so that a record that changes without changing what it points at moves the etag of every page made of it by `old_local XOR new_local`, without walking anything.
- **The refresh** runs in every write (`load`, `delete`, `rederive`), in the same transaction, from the history rows since the last etag transaction (`_etags` in `ids`, so a write made outside the store is made up for by the next). The seeds are the changed records and, for one that is new, gone or has another resource uri, the records that point at it. A seed is walked again from the references; a record made of seeds (found by `deep_references`) is walked again when there are few of them (200), or when a seed's references changed; otherwise its etag is moved by the delta (one update of a column). **There is no limit on how many records a write may change**: incremental was measured at 1M records to cost 0.4 to 1.3 s for 1,000 to 100,000 changed works and 0.4 to 0.8 s for 500 to 50,000 persons (586,000 pages moved), a full rebuild 5.5 s whatever changed, and a write that changed all 300,000 records of a repository 2.7 s against a rebuild of 2.0 s, with no wrong etag. **The time of a record is made by the store and only goes up** (`gracia:modified_at` is never taken from a text, an import or a restore: a new or changed record gets the time of the transaction, a record whose rows did not change keeps its time), so `etags.last_modified_at` never goes down either: a page that loses the record that was its latest (deleted, or another resource uri) keeps its time, and a rebuild keeps it too. There is no backwards case to walk. A full rebuild is only for an empty table (the first time, or after the numbers of the types changed).
- **Order.** The table is kept newest created first (`record_type`, `sort_key` DESC, `record_id`), every write sorts it again before it commits (`_sort_etags`: a new table, swapped in; about 110 MB written and 0.2 to 0.45 s at 1M, the file does not grow). `sort_key` is `created_at` in microseconds, a number (the zone maps of text keep only a short prefix, so an `after=` on a text key does not prune), and an edit does not change it. So a listing is read with LIMIT and OFFSET and no ORDER BY and stops after its page.
- **`backref_totals`** (`{source type: {total_all, total_published}}`): how many records point at this one. Kept by changes (`_backref_changes`, `_backref_totals`): only a seed can change what a record points at, so a write adds and takes off one for each target of a seed whose references or published flag changed, and merges them in when the table is sorted; a replaced row keeps its totals. A rebuild counts from scratch, and the tests check the totals against a recount after every random write.
- **Batches.** `Store.referrers(target, source_type, page, published)` and `Store.records_page(slug, page, published)` return a `Page` (items with their etags, `page`, `pages`, `total`, `total_all`, `total_published`). **Pages are numbered the ordinary way: `?page=1` is the newest 20 and the pages go back in time**, 20 to a page, the last (the oldest) with what is left, the records on a page newest first. Page 1 is the cheapest (offset 0); a deep page reads past the newer ones (1M records, every work: page 1 2.2 ms, the middle 7.4 ms, the last of 39,977 pages 13.7 ms; 5,000 records: 3.8 and 5.1 ms; both totals come with the row). The price of these numbers is that they are not stable: a record that is added moves every record down a place, so every page of the listing changes (and its etag). Numbering from the oldest was built and given up: it keeps old pages as they are (a new record only changes the last page, which then holds 20 to 39 records), but `?page=52` for the newest records confuses people, and a bot walking all the pages of a listing is not a problem. `after=sort_key` was measured (flat 0.7 ms with a numeric key) and left out: it makes a distinct URL for every record; only `?page=N`.
- **The pages a browser gets** (`Accept: text/html`; no `Accept` or JSON gets what it always got): `GET /<repo>/<type>/` is `templates/type_index.pt` (the labels, a link to each, the page links; those who may edit also see what is not published), `GET /<repo>/<type>/<n>` is `templates/record.pt` (label, type, the description from a property with `dash:DescriptionRole` if the record has it, a table of the `dash:KeyInfoRole` properties under their `sh:name`; only web, mail and phone addresses and records are links).
- **Measured at 1M records** (writes include the refresh, the sort and the totals): a work 525 ms, a person 552, a department 579, a university rename (660,000 pages) 597, a type record rename 661, a university given other references 4.7 s (walked again), a full rebuild 5.7 s; reading an etag 0.5 ms. Other repositories are not held up by a long write (the commit is 30 to 65 ms), writers of the same repository wait for it.
- **Tried and not worth it:** numbering the pages from the oldest (above), a Bloom filter per row (slower: 2.3 to 9 ms against 0.3 to 4.6 ms), a min and max of each row's ids (the ranges are as wide as the table, because every record points at its type record), hash ids, a separate edge table, a separate table for the totals, indexes on `records_identifiers`, `records_references` and `slugs` (dropped: 2.8 s against 1.2 s for the commit of 300,000 records, lookups 1 to 5 ms slower).

### Open: chunked, resumable imports (not built; hard, to do)

One file is one transaction, whatever its size (`Store.load`): the commit of 300,000 records took 1.2 s (the unique constraints that must stay), about 4 s at 1M, during which other repositories cannot commit, and writers of the repository wait behind it with a retry that gives up after about 6 s (`LOAD_ATTEMPTS`; `delete` and `rederive` do not retry at all). The same limit hits any long write: a type record or a university renamed is now cheap (0.6 s), but a re-import is not. What is decided and what is not:

- **Roll forward, not back.** Loads replace whole records by key and never delete, so running a chunk again is safe, and a half-finished import is the state of records edited one at a time (every invariant is per record). Rolling back was considered and rejected: a copy of `triples` is not enough (`records`, history, slugs, unique values, counters and etags are all derived, and a restore would wipe what others wrote meanwhile unless every write is locked for the whole import), and DuckLake is a different storage layer (whether it keeps our triggers is unknown). An undo can be built from the history, which has every version of every record per transaction number: restore the version before the first chunk (or delete a record that was new), skipping records edited since.
- **The continuing transaction is the jobs framework** (`gracia/jobs`, Luigi): batches that are done are not done again, so a stopped or failed job goes on where it was. The import becomes a stage like `Rewrite` (batches of about 50,000 records, each its own transaction). It relates to the `Ingest` stage the Jobs section describes (all batches staged without a transaction, then one short transaction that merges and writes a marker, nothing committed if anything failed): that one is atomic but its last transaction is as long as the import, so for big imports it has to become several, and atomicity goes.
- **Chunk after the flatten**, by record, not the file: splitting Turtle by hand is hard (prefixes, blank nodes), and `flatten_triples` already puts every record's rows together. The hooks run once over the whole batch as now.
- **The etags during an import.** The refresh can run once at the end (it catches up from the history). Meanwhile the etags of records that were *updated* (not new ones) are stale, and a stale etag can answer 304 for a changed page: while an import is running the index view must not use the stored etag (the `_etags` marker is behind the last transaction), and walk the references as it does for a repository with no etags.
- **Open:** whether a failed import that leaves the chunks that had committed is acceptable (it is: every load is a merge, so running it again is safe); a time budget for the retry instead of 20 tries; progress and the stale-etag guard as one marker; `put` of a very large graph through the API (a size limit, or the same chunking).
- **A DuckDB bug seen while measuring:** a single `UPDATE` of 200,000 rows of `triples` (which has statement triggers) fails with an internal assertion error in `PhysicalUpdate::Sink`. The store never updates that table (it deletes and inserts), so it has not come up; worth reporting if the store ever has to.

## Jobs

Long work over many resources or files: validate a schema revision against every record of a type, export, import, fetch and derive files (text, thumbnails, embeddings). Not stored in RDF: SQL tables and a directory per job.

- **Jobs run on Luigi** (decided after a spike on 100,000 persons, 2026-11). A job is a list of stages, `[{"stage": "Export", "params": {...}}, {"stage": "Validate", ...}]`, and every stage is a Luigi task class: Luigi's register finds it by name, resumes by outputs (a batch that has its files is not done again, so running a failed job again continues where it stopped), runs tasks in parallel and times them out. Why not our own runner or Celery: battle-tested code, extension points we may want (targets in S3, GCS or other storage, configuration, notifications), and no server. The costs: Luigi's vocabulary (task, parameter, target, requires, build) stays inside the jobs package, and its local scheduler is documented as for development (we run one per job process; deduplication and the visualiser are not needed, and the page is ours). Measured: Luigi itself adds about 1 ms per task in one process and about 5 ms with workers (each task forks), so batches stay coarse (thousands of items, a fraction of a second or more of work); 100,000 pages through Export and Validate took about 11.5 s with 4 workers, against about 26 s for the sequential runner it replaced; the speed-up with more workers is clearly sublinear (about 3x at 16 in the spike), the database owner being the likely limit.
- **Observed once, not reproduced:** a `serve-db` owner that did not exit on SIGTERM, minutes later, after a job had run through it (161 threads, which turned out to be what an idle owner has anyway, so it says nothing). Seven attempts to repeat it did not: the same sequence again, with the `uv run` wrapper and a SIGTERM to both processes; an owner with nothing done to it, after `repo create`, after `jobs list` and after `jobs validate`; and an owner whose client was killed with SIGKILL while attached (with and without a repository store open) all exited within a second. If it comes back, `serve_db` should wait for `quack_stop` and the checkpoint only for a bounded time and then exit (the WAL is replayed at the next start), because a stuck owner keeps the file lock and the port until it is killed with SIGKILL.
- **Not built yet:** the `Ingest` stage (all the batches loaded into a staging table without a transaction, then, when every stage before it is done and green, one short transaction that merges and writes a marker row: nothing is committed if anything failed; designed and tried in the spike, not built); sources whose size is not known (a crawl, a zip): a streaming first stage that writes batches as it goes, after which the later stages start (Luigi's graph is static, so there is no overlap with that stage; `plan` is then not a count); passing data by reference and compressing or removing the intermediate batch files after a job is done; chains and defaults from `luigi.cfg` for jobs run from cron; the central scheduler and workers on other hosts (they would need shared storage and the owner); a per-call retry helper for HTTP; limiting the number of running jobs; `gracia jobs trace`; uploads of initial inputs.
- **The pipeline** (`gracia/jobs/`; tests in `tests/test_jobs.py`). `Stage` (`stage.py`) is the base class of a step: it is a `luigi.Task` with the parameters `job_dir`, `repo`, `n` (the batch) and `chain` (the JSON list of the stages up to and including this one, so a change in a later stage never changes the id of an earlier task). Its `requires()` is the stage before it for the same batch, so stage *k* of batch *n* needs only stage *k-1* of batch *n*: the stages overlap and the batches run in parallel. A stage author writes `process(items) -> (passed, rejected)` and nothing else; the base class writes three outputs in `<job_dir>/<index>-<Name>/`: `batch-<n>.jsonl` (what went on), `rejected-<n>.jsonl` (what stopped here, with a `reason`) and `stats-<n>.json` (`processed`, `passed`, `rejected` by reason, a few `samples`), and a task is done when all three exist (written atomically; the data last). The counters travel by file: the next stage reads the previous stage's output, the job process adds the stats files up; the scheduler's memory cannot be the source, because a finished task's message is gone and a restarted process lists none of the tasks that were already done. A stage that rejects nothing and passes every item as it got it does not copy: its output is a hard link to the file of the stage before (free, shared, and the earlier stage's file stays; a stage that writes new files never edits in place, so the link is safe). A job names a source first (`Source`: `plan()` says `{batches, estimate}`, and `Plan` is a task of its own, done once) and the rest after it; `jobs.spec.validate_spec` checks the names against Luigi's register and the parameters against the class (a value from JSON is taken through the parameter's own `parse(serialize(value))`: Luigi does not check types of values passed in code; `job_dir`, `repo`, `n` and `chain` are the job's, not the author's). The policy for errors is to crash and resume: a task that raises fails the job (`StageFailure` carries a message for a person; anything else is reported as `Type: message`), the failure is appended to `errors.jsonl` by an event handler (the tasks run in forked workers, which cannot tell the process that started them), other batches go on, and running the job again redoes only what has no files. Retries belong around a call (a GET), not around a batch. A validation violation is a result, not an error: the record is rejected with its violations.
- **The stages that exist** (`gracia/jobs/builtin.py`). `Export` (`res_type`, `chunk_bytes`, 0 = one file; the validate job passes 20,000,000) is a source whose plan *is* the export: one `COPY` of the `source` column of `records` (`Store.export_chunks`; CSV with quote and escape off, so the N-Triples go out as they are, a blank line between records) into `00-Export/`, written by DuckDB with `FILE_SIZE_BYTES`, `FILENAME_PATTERN`, `FILE_EXTENSION 'nt'` and `RETURN_FILES`. Measured on 1.5 million records (1.2 GB): 0.4 s, 57 files; the files are written at the same time, so none is known to be complete until the `COPY` returns (a file is not done when the next one starts), which is why the plan waits for it and the files are moved into place (`batch-NNNNN.nt`) after. DuckDB looks at the size after every 2048 rows: a file can be over `chunk_bytes` by that many records, and fewer records always make one file. A batch is a file; the next stage reads it with `read_items` (records split at the blank lines, `{"id", "source"}`). `Validate` (`type`, `schema`: a file of the type, by default the one the type is on, or a candidate revision) checks the records of a batch with `shacl.validate` and rejects `violation` (with the violations) and `no_content`; `PinSchema` copies the schema file into the job (`schema/<type>/<file>/schema.ttl`, with the checksum) once, before the first batch, so the whole job checks against the version it began with and can be repeated. The plan, the stages' parameters and what the job offers: `rejected.jsonl` (every rejected item of every stage, with the stage's name) is made when the job is done and is the download. Three more write: `Rewrite` (the hooks again on the stored records of a type, batches of `size` record numbers, `Store.rederive`), `PurgeSlugs` (`Store.purge_slugs`, one batch) and `RebuildEtags` (`Store.rebuild_etags`, one batch; what passes on are the records whose etag was wrong, none when they were all right).
- **One process per job**, started by the server and detached: `subprocess.Popen([python, "-m", "gracia", "run", <uuid>], start_new_session=True, stdin=DEVNULL, output to job.log)`, a fresh interpreter that leads its own process group, survives a restart of the server and runs `luigi.build` over the last stage of every batch. Luigi forks a worker per task: `gracia.jobs_workers` of them at a time (default 4, no more than there are batches, and one when the database is a file or in memory, because a worker is another process and reaches the database only through the owner: `jobs/context.py` hands the job process its own application and gives every worker a connection of its own to the owner, never the parent's). Forking a multi-threaded process (the snapshot thread, DuckDB's threads) makes Python 3.12 warn that it may deadlock; the workers never touch what the parent holds, the tests run it (31 process tests, many parallel full runs), and Luigi pins Python below 3.14 (where fork stops being the default); a forkserver would lose the context the workers inherit. It is a risk to watch, not a known failure. Limits are set inside the process or with `systemd-run`, never with `preexec_fn`. Under systemd or in a container a detached child stays in the cgroup of the service and stops with it: the jobs then run as a unit of their own.
- **Failure and cleanup.** `gracia run <uuid>` runs inside one try/except. A task that fails writes its message to `errors.jsonl` (an event handler, in the worker); Luigi lets the other batches go on; when the build is over the job is `failed` with that message as `error_msg` (or `done`, or `stopped`), and the process exits non-zero (0 done, 1 failed, 3 stopped, 2 nothing to do). The updates are conditional (`WHERE state IN (...)`), so the process and the server never undo each other, and the process also writes its last words to `exit.json` first so that they survive when the database cannot be reached. When the operating system kills it (the out-of-memory killer, a reboot) nothing can be caught: a status call (and the list) reconciles on read. A job that is not in a terminal state, whose `host` is this host and whose pid is gone, is dead: the pid is compared with its start time (`pid_started`) and a zombie counts as dead; it is then set to `failed` ("process disappeared", or the text of `exit.json`), and its files stay, so that it can be started again and goes on where it was. A job whose process was just spawned is not judged. On another host the pid cannot be checked, and an old `heartbeat_at` (written with every snapshot, every second) is the signal.
- **Commands (`gracia jobs ...`).** `gracia jobs list` (state, repository, the stage the job is in, batches done of total, how many rejected, times and when the download expires; `--state`, `--repo`, `--json`), `gracia jobs show <uuid>` (the row and a line per stage with its counts and samples), `gracia jobs log <uuid> [--raw] [--all] [--follow]` (`luigi.log`, or `job.log` with `--raw`: the last 16 KB, or from the start, and on with `--follow`), `gracia jobs create <file|->` (a job as JSON, in the format of the spec), `gracia jobs validate --repo R --type K [--schema FILE] [--size N]` (`--batch-size` is an alias), `gracia jobs start <uuid>` (starts a `queued` job, or restarts a `stopped` or `failed` one, which goes on where it was; adds one to `attempt`; refuses a job whose process is alive), `gracia jobs stop`, `gracia jobs clean`. `list`, `show`, `log` and `clean` reconcile first (a job whose process is gone is set to `failed`). `gracia run <uuid>` is what a job's process runs; it is not meant to be typed.
- **Stopping: `gracia jobs stop <uuid> [--grace SECONDS] [--now] [--by WHO]`**, and the server uses the same command. A stop from the API spawns `gracia jobs stop <uuid>` detached and answers 202: the grace wait must not block a request, and a stop in progress survives a restart of the server. The command sets `stopping` with a conditional update (so two stops at once are one), sends SIGTERM to the process group and waits up to the grace period (default `gracia.jobs_stop_grace`, 15 s). The job process handles SIGTERM by setting its stop flag and asking Luigi to stop taking work (Luigi's own graceful stop, SIGUSR1, sent only when Luigi's worker has installed its handler: before that SIGUSR1 would end the process): what runs finishes, nothing new starts, and the build returns as `NOT_RUN` with exit code 0, which is why the process keeps its own flag to say `stopped`. After the grace period the command sends SIGKILL to the whole group, which takes the workers with it, and sets `stopped` with `finished_at` and a message (who stopped it). `--now` skips the grace period. A `queued` job is just set to `stopped`; a job in a terminal state is left alone; a job whose process is already gone becomes `stopped`. Because it ends in SIGKILL it signals only what is certainly the job's process: the host must be this host, `pid_started` must match the start time of that pid, and the process must lead its own group before `killpg` is used. A batch that is interrupted leaves no partial result (outputs are written to a temporary file and renamed), so a restart does it again.
- **Who may see and control a job.** A job is a node in the traversal tree (`/<repo>/jobs/<uuid>`) with its own ACL, closed with `DENY_ALL` like the other private nodes, so the default `view` that everyone has does not apply to it. Three permissions: `view` (the status, the progress and the log), `stop` and `download` (the `download_file`). The creator holds all three on their own job and administrators hold everything (`ALL_PERMISSIONS`); a job started from the CLI has no creator, so it is for administrators only. Most bulk work will be done by administrators anyway, and keeping each action a named permission means another group can be given one of them later by one more ACL entry (a group that may stop but not download). The uuid is an identifier and never the only check: it appears in links, lists, logs, the process list and a directory name, and a result file can hold data that its reader may not otherwise see (an export started by an administrator). The creator is stored as the user key `user:<n>` (`created_by`, with `n` the number of the user's record, which never changes, unlike a user id that can be edited), and the principal the security policy gives a logged-in user is that same `user:<n>` (today it is `user:<userid>`: to change when the jobs are built), so the job's ACL simply grants `user:<n>`. The CLI has operator rights and needs no permission. Starting a job needs the rights for every task in it, checked at creation.
- **Cleanup: `gracia jobs clean`** (the command is for cron; nothing is deleted by anything else). It removes the rows and the directory of every job that is in a terminal state (`done`, `stopped`, `failed`) and finished more than 8 hours ago: `--older-than` takes `30m`, `8h`, `2d`, and its default is the setting `gracia.jobs_retention` (default `8h`); `--dry-run` only reports. A job that is queued or running is never touched; a job that has just been reconciled to `failed` counts from that moment, so it is cleaned later and not at once. It reports what it removed (jobs, bytes). It must be safe to run twice at the same time: the delete of a row is conditional, removing a directory that is already gone is not an error. A directory is only removed when its name is a uuid and its resolved path lies inside `gracia.jobs_dir` (no symlink or odd name from the database can point it elsewhere); directories without a row (left by a crash) are removed after the same period. The window is also how long a `download_file` can be fetched, so the status shows when it expires (`finished_at` plus the retention); after cleanup a job can no longer be restarted. A creator should be able to delete a finished job early.
- **The database owner is `gracia serve-db`** (decided), so the web server and the job processes are both clients of it over Quack (`gracia.db = quack:...` for `gracia serve`). `gracia run <uuid>` reads the token the way every command does: from the token file next to the database (found through `<db>.owner`), or from `config.ini` (`gracia.db`, `gracia.db.token_file`); the server passes `-c` and `-d` explicitly when it spawns the process, so the task connects to the same owner. Quack rules apply to task code: it works through `Store` (which has the remote path), and a `COPY` runs in the owner process, so the job directory has to be writable by the owner (true today: Quack is localhost-only, same machine and user).
- **The table.** `_gracia.jobs`, one row per job (`jobs/db.py`): `id` (uuid), `repo`, `created_by` (`user:<userid>`, NULL from the CLI), `job` (its name, `validate`), `subject` (what it is about, the slug of a type; the panel filters on both), `stages` (JSON: the definition, written once), `progress` (JSON: the snapshot of every stage, written by the job process only), `state` (`queued`, `running`, `stopping`, `stopped`, `failed`, `done`), `message`, `error_msg`, `download_file` and its content type, `host`, `pid`, `pid_started`, `attempt`, `code_version` and the timestamps (naive UTC; `heartbeat_at` is written with every snapshot). There is no table of tasks: the earlier design had one, and a database that still has that shape loses its (finished) jobs the first time the new code opens it. The snapshot is `{"stages": [{name, state (pending, running, done, failed), batches: {done, running, total}, processed, passed, rejected: {reason: n}, samples, total, estimated}], unit, updated}`; the total of the first stage is the estimate of the plan, that of a later stage is what the stage before it passed on once that is done; the panel draws a bar by batches, and a sliding one while the total is not known. Writes of the row retry on a transaction conflict (`JobsDb._write`): the job process and a stop change the same row.
- **`gracia.jobs_dir` in `config.ini`.** The directory that holds the job directories, read by `gracia/config.py` now (a relative path is taken from the directory of the config file, like the other paths; the setting is optional) and used when the jobs are built. Its default, next to the database (`<database file>.jobs`), only works where the database file is known, so a client that connects to a `quack:` owner needs `gracia.db.file` or the setting itself; in production set it explicitly, because the directory must be writable by the process that owns the database (`serve-db`, where a `COPY` runs) and by the job processes, and it may be on another path than the database. Moving it only affects jobs that still have files: finished jobs are cleaned after the retention period.
- **The directory** `<jobs_dir>/<id>/`: `plan.json`, one directory per stage (`00-Export/`, `01-Validate/`: the three files per batch), `schema/` (the pinned schema files), `errors.jsonl`, `rejected.jsonl` (the download), `summary.json` (the last snapshot), `luigi-summary.txt` (Luigi's own account of what ran), `exit.json` (the last words of the process, written before the database is touched), `luigi.log` (Python logging from the process and its workers: one file, each record a line with the process id, so interleaving is by line) and `job.log` (what the process printed: it is started with its output redirected).
- **Threads or processes.** Measured: `pyrudof` (written in Rust) releases the GIL for part of its work: 1.5 to 2.5 times faster on 4 threads; worker processes were not better for validation (handing a batch over by pickle costs 13 ms per 1,000 resources, about 40% of the validation work). Processes are for heavy per-resource work, for isolation and for killing (`pyrudof` has no timeout, so a runaway validation cannot be stopped in a thread; a per-batch timeout needs the task to run risky work in supervised children, for which the task base class offers a helper); embedding libraries release the GIL themselves and want one warm process that holds the model.
- **Attachments, later.** Needs a content-addressed file store, a relation from a record to its files, and derived files named by (source checksum, derivation, version): idempotent, retry-safe, skip-if-exists and good for caches (it ties into the ETag). PDFs are untrusted input: their tools run confined as above.
- **Monitoring and a management screen** (wanted): every job with its state, task and progress, the job log (tailed), the result files, the processes (pid, age, last heartbeat), cancel, restart and kill. It reads the table and the directories.
- **Considered and not chosen for now:** Celery (needs a broker and workers, two sources of truth, its strength is distribution across hosts, which we do not use; the nearest relative of the App Engine task queue) and our own runner (what we had: it worked, but overlap of stages, parallel batches, timeouts and resume would all be ours to maintain). A central Luigi scheduler is possible later; the serialized form of a task (family and JSON parameters: `to_str_params` and `from_str_params` round-trip) is what a pull-model worker on another host would claim from the table.
- **Open:** how uploaded initial inputs arrive (with the creation request, as multipart, for now); whether workers on other machines are a goal (the job directory would have to be shared); how long results and directories are kept.

## Times, caches, the change queue and search (built, 2026-11)

What follows the data: the times of records, what is kept ready for a request, the queue of what changed, and the search index. Code: `actions.py`, `cache.py`, `search.py`, `extensions/search.py`, `views/search.py`, `views/repository.py` (`search_page`), `views/manage.py` (the Stats tab), `docs.py`, the trigger steps in `store.py` and `assets/sql/` (`records.sql`, `etags.sql`, `macros.sql`); tests `tests/test_cache.py`, `test_actions.py`, `test_stats.py`, `test_search.py`, `test_search_job.py`, `test_graph_jobs.py`, `test_record_graph.py`, `test_repositories_last_modified.py`; the measurements are throwaway scripts in `bench/` (nothing in `src/` uses them). Existing databases are not migrated (decided): the tables and columns below are made with the schema, so a repository made before them is made again.

### Times

- **`modified_at` is never set from outside (decided).** A text, an import or a restore cannot give a record its time: a record that is new, or whose rows changed, gets the time of the transaction (never earlier than the one it had), and one whose rows did not change keeps its time (`predicates/gracia_modified_at.py`). Only a store that has the hooks (the web app, the CLI import, `node.store()`) enforces it: a bare `Store.put` or SQL still writes any value, and the tests use that to make fixtures with chosen times. So the time of a record only goes up.
- **`etags.last_modified_at` only goes up, and is the time of the write whenever the etag changes.** It is the latest `modified_at` of the closure, never earlier than the value the row had, and the time of the transaction when the new etag is not the old one: a page that loses a record it was made of (deleted, another resource uri) has another etag and another time. A rebuild gives the same rows as the writes (it keeps the time of a row whose etag is the same, and bumps one whose etag differs). The `backwards` case of the refresh (a record that moved back in time, so its dependents are walked again) was removed with it. So "`last_modified_at` > t" finds every page whose etag changed after t; a deleted record has no `etags` row (it is in the history, and its number is in `slugs`, flagged deleted, with the time).
- **`main.repositories_last_modified_at`** (`repo_id`, `last_modified_at`; created with the schema of a repository, in the `main` schema of the database): upserted with the time of the transaction by one of the trigger steps on `triples` (so by a write outside the store too) and by `_rebuild_etags`. A write into a schema updating a table of another works, and repositories do not hold each other up (different rows; measured with a transaction held open in one while another wrote and committed, and six repositories writing at once).
- **The sizes.** `records.bytes` (the size of `source`), `etags.bytes` (the same) and `etags.closure_bytes` (the sizes of the sources of the record and of everything it is made of, kept exactly by the walk and by the delta, and by a rebuild): what a batch is measured in.

### The N-Triples of a record

- **`encode_ntriples_uri`** (`macros.sql`, replaces the JSON string and string replace): space, `<`, `>`, `"`, `{`, `}`, `|`, `\` and `^` in a uri are percent-encoded; control characters, DEL and the backtick are removed; `%` is left alone, so a uri that is already encoded is not encoded twice (decided after trying it with `%` -> `%25`, with fewer characters encoded, and with the spaces removed). The benchmark: 0.26 s to 0.4 s per million uris, nothing a bulk write notices.
- **`history.source` is the `records.source` of the statement**, copied by the trigger step, not made again.
- **Blank nodes are `_:b<record id>_<n>`**, made of the number of the blank node that `loc` stores, instead of a `uuid()` per call: the same every time, unique across records, valid as an `rdf:nodeID` (a uuid that starts with a digit is not, and RDF/XML written from one cannot be read back), 21% shorter. So the sources and graphs of many records can be put together and the duplicates fall away. **Canonicalizing each file (RDFC-1.0, any of its four algorithms) does not do that**: the canonical labels depend on the rest of the file, so one record gets another label in every file (two articles sharing 513 records: 8,815 triples merged, 6,095 true).
- **`record_graph()`** (`etags.sql`): a table macro, not a view, because `_sort_etags` replaces `etags` in every write and a view on it would stop that. One row per record of `etags` with `graph`: a TriG graph named by the record with its own source first, then those of its `references` and `deep_references`; a filter on `record_id`, `record_type` or `last_modified_at` is applied before the sources are read (3 ms for one record at 66,000). The export uses it.
- **What pyoxigraph does (measured, 0.5.13).** `ox.parse` keeps blank node labels, so a `Dataset` or `Store.extend` of parsed quads merges identical nodes; `Store.load` and `bulk_load` give every load new labels (loading the same file twice gives two copies); the same triple in two named graphs stays two quads; the RDF/XML it writes is flat, in no fixed order, and not checked: a predicate that ends in a digit or a `/` or a control character in a literal gives XML that is not well-formed (decided not to validate for speed; to do if it shows in real data).

### The caches (`cache.py`, `Application.cache`)

- **Change detection.** The signature is the modification time and size of `<db>` and of `<db>.wal` (a commit only touches the WAL; the file itself changes at a checkpoint), taken **before** the table `repositories_last_modified_at` is read, so a commit in between shows at the next check. Without a file to watch (a memory database, or Quack from another machine) the table is read every time; it needs a local disk (`gracia.db.file` for the web server over Quack). `check()` is 1.7 µs when nothing changed.
- **Five LMDB caches, one environment each** (directories under `gracia.cache_dir`; a process opens an environment once, so they open lazily, and reading the types opens none). Three are *stamped* (`StampedStore`): the key is `repo \0 repo_last_modified_at key`, with the time of the last write of the repository in microseconds (`main.repositories_last_modified_at`, seen by `check()`). A reader takes that time **once** and uses the same key to read and to write, so a request that was running when the repository changed can only write under the old time, never the new one (there is no shared dict and no lock). The first time a stamped cache sees a new time for a repository it deletes what is under the older ones with a batched ranged delete (`delete_range_batched`: write transactions of 5,000 keys, so readers and writers of other keys are not held up). Nothing is refreshed on a write: an unrelated request would pay for it. A full map is emptied and filled again.
  - **etags** (`etags/`, `EtagStore`): `record_id (4 bytes) -> etag` (16 hex digits); an empty value is a record that is not there (remembered too, so a deleted record is looked up once). `Cache.etags(repo, ids)` returns `{id: etag | None}`, asks for the missing ids in one query. It does **not** keep the deep types: the index view mixes the version of every type's schema into the page etag (`views/index.py`; a global hash, so a schema change changes all pages) and takes the slugs of the shapes from the records of the page. To do: the HTTP etag of a page should also hold the hashes of the js/css assets (the shacl/xslt files are named by their versions, so a change of one is a change of the type record, and of the data etag).
  - **slugs** (`slugs/`, `SlugStore`): `rec_type \0 slug -> record_id (4 bytes), is_deleted (1 byte)`. `Store.slug_lookup` gives `(record_id, is_deleted)`; a slug that is not there is not kept (it may be made next).
  - **referencing** (`referencing/`, `ReferencingStore`): a page of `Store.referencing_records` is `md5(arguments) -> the record ids`, packed 4 bytes each (big-endian, no length: the number is `len // 4`); the total is a key of its own, `md5(arguments without offset and limit, return_count_only) -> 8 bytes`, so every page of a listing shares one count (`Cache.referencing_records`, `referencing_records_total`; each takes a `load` that asks the database). The page and the total are two calls and two stamps, not one snapshot: a write between them can make the page count off by one until the next request. A hit is 7 µs (a miss 1.6 ms, of which the store opened is most).
  - The graph and doc caches (below) are the other two. **Sizes** are the most each file may hold, set in `config.ini` as `gracia.cache.<graphs|docs|etags|slugs|referencing>_size` (`256M`, `1G`; `config.parse_size`): defaults 2 GB, 2 GB, 256 MB (about 2.5 million etags), 64 MB, 512 MB. A file only grows as far as it is filled. One environment each so that a full graph cache does not empty the etags and one writer does not wait for another; without a cache directory each gets a temporary directory that lives as long as the process.
- **The graph cache** is LMDB (`gracia.cache_dir`): key repository + record id, value the etag it was made at and the RDF/XML of the record and everything it is made of (`Store.closure_sources`, the blank nodes as they are, not canonicalized). An entry is used only when its etag is the current one, so nothing is ever invalidated (a stale entry is never matched, and the next write of the record replaces it); a map that is full is cleared. A hit is 13 µs (a record of 550 records, 388 KB), a miss 13 ms. Many entries are written in one transaction (a transaction each was 0.47 ms per record, nearly all of it the sync; 0.003 ms in one).
- **`Store.referencing_records(referenced_record_id=None, record_type=0, offset=0, limit=20, include_non_public=False, include_deleted=False, state=None) -> [record_id]`** and `count_referencing_records(...)` (the total), read from `etags` in its own order (newest created first, no `ORDER BY`); the views turn page numbers into offset and limit (`store.page_window`). Give the record that is pointed at (`list_contains("references", id)`), the type (a number; alone it is the records of that type: `record_type = type_slug(n)`, no arrays are read), or both; none is a `ValueError`. The type index (`views/type.py`) uses the type alone. `state` filters on `etags.state`.
  - **`include_deleted`** (OAI-PMH) is only for a `record_type` (no referenced record, no state: a record that is gone has no references and no state). The records of the type that are there are merged with the deleted ones, from `slugs`: the row that is the number of the record as a slug (made when it is deleted, flagged `is_deleted`), whose new column `slugs.modified_at` is when it was deleted; the page is sorted on `modified_at DESC, record_id` (`etags` is in the order of creation, so there is a sort: 3 ms against 1 ms at 76,000 works and 3,000 deleted). A deleted record has no etag, and `Cache.etags` gives None for it.
  - **`state`** (`gracia:state`, `uri.STATE`) is the last column of `records` and `etags` (and `etags_new`: the inserts are by position), NULL when the record has none, read from the top level of the record by `record_rows`; nothing writes it yet (no form or predicate). Measured with `bench/etag_refresh_scale.py` at 100,000 records: writes 3% slower (310 against 299 ms for a work), reads of a batch the same.
  - `bench/referencing_deleted.py` measures the deleted listing and the cost of `slugs.modified_at` (flagging 80,000 slug rows 1.5 against 0.9 ms).
- **Chosen over:** rocksdict (one writer process per directory), the pyoxigraph store as a key-value store (it is a quad store: the blob in six indexes), a DuckDB table (writes on read paths, an index the commits would pay for), files (a directory per million). **Considered and not built:** a rdfxml file for each record's own source, merged by XSLT or by parsing (the parse of 10 documents is 87 ms against 12 ms from `records.source`, which already is the cache; and each article's closure duplicates its 500 authors); a global pyoxigraph store with a graph per record (10 ms in memory against 17, RocksDB slower, and the two commits are not atomic; it can be rebuilt at night for SPARQL, nothing depends on it).
- **The export (`Export`) got `graphs` and `queued`**: TriG chunks, each graph after `# <etag> [<action>]`, written by DuckDB (`Store.export_chunks`, `export_queue`, `_copy_chunks`); the plan also says `bound`, the last transaction before the export. `UpdateCache` (job **Update cache**) fills the graph cache from it: each graph's N-Triples into a Dataset of its own (about 8 ms for the 500-author article; one Dataset of the whole chunk with each graph taken out of it was 33 ms), in one LMDB transaction per file.

### The change queue and the worker (`actions.py`)

- **`actions_queue(transaction_id, record_id, action)`** in each repository, no index, written in the transaction of the write: `insert` (new, or deleted before), `update`, `delete` by the trigger steps that fill the history (one row for a record and a transaction: a replace is one `update`), and `ref_update` by one set-based insert in `refresh_etags` for the pages that were walked or moved because something they are made of changed and that no write named (400,000 rows: 8 ms), and by `rebuild_etags` for the pages whose etag differs. **Per repository, not global (decided):** the transaction numbers are per repository, the rows must be in the transaction of the write, and one repository's slow follower must not hold the others. A row says that a record changed, not how, and handlers read the current state, so processing transaction 5 after 6 cannot make an older version win; delivery is at least once (the rows are taken off after the handlers succeeded), so a handler must be able to do a record twice. The order of the transaction numbers is the order of the commits (the counter row serializes the writers).
- **`process_batch`**: the oldest rows, up to `BATCH` (5,000) records and `BATCH_BYTES` (20 MB of `closure_bytes`; the first record is always taken), the newest action of each record; the closures of the records that are there (`Store.closure_sources`: the ids of the parts from `etags`, then the sources by id: one statement that joined `etags` and `records` read all of `records` at every call, 13.8 ms against 0.8); `deliver`: a Dataset for each, the RDF/XML in the graph cache, the graphs of deleted records taken out, **one `RecordsChanged` event for the batch** (`changes`, and `graphs`: a Dataset by record uri; one Tantivy commit for the batch, never an event for each record), and only then the rows off the queue (up to the transaction `take_actions` saw). `process_pending(application, registry, repo=None)` is the manual way (tests, scripts); `Store.catch_up_etags` makes the etags of a write outside the store first.
- **The worker** (`Worker`; settings `gracia.worker`, `gracia.worker.batch`, `.batch_bytes`, `.poll`): one thread in each web process, started when the application is made, woken by the response to a request that is not a GET, started again by `Cache.check` when it died. The repositories that may have something to do stand in a line; a turn handles **one batch** of the first and puts it at the back if the batch was not empty (a backlog does not hold the others up; the switch costs a lock attempt and a query, about 50 µs and a few ms); a repository joins the line when its time in `repositories_last_modified_at` moved (read once per change of the files: not for the rows the worker takes off, nor for the progress of a job) and at the start; a failure waits its own pause (2^n s, at most 60) and the others go on. A `flock` per repository (`actions-<repo>.lock` in `gracia.cache_dir`, else next to the database file) keeps processes off one queue, the system lets go of it when the process dies; a handler that opens a Tantivy writer runs under it. **Where it runs (decided):** a thread of `gracia serve`; not in `serve-db` (handler, extension and native code must not be able to take the database owner down, and the owner has no Pyramid registry), not a chain of requests (lost wake-ups, and a Quack attachment of 54 ms for every hop).
- **The job "Process pending actions"** is `Export` with `queued` and `ProcessActions`: one `COPY` of the graphs of the queued records into 32 MB chunks, then a stage per file that `deliver`s it and takes its rows off (the lock per batch, so not at the same time as the worker). The first version, a Luigi task for 100 rows, took 0.2 s a task (a Quack store, the queries, Luigi): 3 minutes for 100,000 small records. Now about 3 s per 100,000 (the worker's direct path: 6 s). The jobs of the repository's Jobs tab are now `rebuild_etags`, `update_cache`, `rebuild_search` and `process_actions`.
- **Not built:** the event right after a single `put()` in the request (it would run handlers in request threads, against the single Tantivy writer, and one commit per save; waking the worker is the same speed), a pause that lets a small recent batch grow before it is delivered, skipping a batch that keeps failing (it is retried with the backoff for ever), staging the Tantivy writes in LMDB (a durable stage and a committer that deletes an entry only if its version is the same; worth it if the commits of a trickle of saves, or making the documents, turn out to cost).

### Search (`search.py`; setting `gracia.index_dir`)

- **Tantivy, one index for each repository and index definition** (`<index_dir>/<repo>/<name>`), with `<name>.json` beside it: a hash of the definition (its fields). An index made for another one is **stale**: it is not written to (the Stats tab says it needs a rebuild), and keeps answering what it had. What Tantivy does (measured, tantivy-py 0.27): a writer holds an exclusive lock for as long as it lives and a second one fails at once (`LockBusy`; readers are free and `reload()` after a commit); `add_document` accepts anything and the error comes at `commit()` for the whole batch (so every document is checked first: `check_document`, and the ones that are not right are left out and logged); a date must be a `datetime`, not a string; a field the schema lacks is dropped without a word (reported); an update is a delete by `record_id` and an add; a text field is always indexed (`indexed` is for integer, boolean and date; `fast` is passed for text and json too); 50 indexes are made and filled in 0.6 s.
- **The document is the doc of the record** (see Docs below): `IndexDefinition` is a name and fields only (no stylesheet, no types: every record is in the index). The handler takes `event.docs` (and makes the ones the event lacks, when there is no doc cache, with `Cache.docs_made`), checks them (`check_document`; **a field the schema lacks is no problem and is left out**, `_for_tantivy`), and writes them with one commit. The job Rebuild search makes the docs of each batch with the doc stylesheet of the repository. A change of a doc stylesheet does not make an index stale; the records change, or the job Rebuild search brings the rest up to date. `docs_made` failing in the handler (a stylesheet that does not compile) fails the handler and the batch is retried with the backoff: nothing is lost, the queue waits.
- **The handler** `on_records_changed` (a subscriber of `RecordsChanged`, registered when `gracia.index_dir` is set; `Application.indexes`): the batch's datasets are merged into one RDF/XML, one XSLT run per index, the check, one writer and one commit; 0.079 ms a record (8 s per 100,000). **The extension `search`** (`extensions/search.py`): on unless turned off (a repository that never said has it on, settings are not migrated), a repository that has it off is not indexed. Settings: `indexes`, each with `name`, `stylesheet`, `types` and `fields` (`name`, `type`, `tokenizer`, `stored`, `indexed`, `fast`; checkboxes with labels). The repository ships with one, `records`, with the fields of `search.RECORDS` (`record_id` fast, `record`/`type`/`slug`/`resource_uri` raw, `label`, `text` not stored, `published`, `modified`, a `data` json field for what a type adds). **The definition is fixed for now (decided):** the form shows it, and the form, an import and `save_settings` refuse any other, like the ARK settings; when schemas can be edited the strict check goes and a changed definition is a stale index.
- **`<record>/index.json`** (admin only, permission `debug_index`): what the index would be sent for the record, made from the cached graph by the same stylesheet; `?debug=input` is the RDF/XML it is given, `?debug=check` the document and what is wrong with it for the schema, `?index=` another index.
- **The job "Rebuild search"** (`Export` of the graphs, then `IndexRecords`): every batch is run through the stylesheet and added to `<name>.building-<job id>` next to the index that answers (one writer at a time per directory, a lock file), each batch leaves a mark (a job run again goes on where it was), and the last batch to finish swaps the directories under the repository's lock (the worker is not writing then) and queues again what changed since the export (`Store.requeue_changes_since(bound)`: the records written, those that are gone and the pages that changed) so that the worker brings the new index up to date; the old one answers until the swap. 20,000 records in 1.8 s (about 9 s per 100,000). **A bug found in use:** `application.indexes` is only set when the Pyramid configuration is made, which a forked worker process of the job has not done yet when its batch starts: the stage makes the configuration first (the test runs the stage on a process that has not).
- **The page of a repository for a browser** (`GET /<repo>/`, `Accept: text/html`; JSON, also for no `Accept` or `*/*`, is what it was: decided inside the one view, because a second view chosen by `Accept` took the requests without a header): a search box and, with `?q=`, the best 20 of what the `records` index finds (label first, then slug, text, key and resource uri; Tantivy's query syntax, read leniently, so a half-typed query still answers). **Only what the caller may see:** records of types they may view (a check per type, not per record), and records that are not published only for those who may edit that type; `Cache-Control: private`. The link of a hit is `request.resource_url(type, slug or number)` (the `slug` is a field of the index, so no record is read for it). Temporary and minimal. **The logo of every page goes to the repository** the page is in (`views.home_url`), else to the application.
- **The Stats tab** of the repository's manage page: *Types* (records, published, size, average, latest change), *Cache* (the pages, what they are made of, the etags in memory, the graphs kept and their space, an **Update cache** button), *Search* (each index, its state, the documents against the records it is meant for, its size, a **Rebuild search** button) and *Pending actions* (the state of the worker for this repository, what waits, the oldest, a **Process pending actions** button). The numbers are those of the moment the page was made (a Refresh link). The jobs it starts are followed in a dialog of the tab itself: a dialog inside a hidden tab cannot be seen, so a panel that is not on screen no longer opens one (`jobs.js`).
- **Open:** schemas that can be edited and more indexes (extra indexes per type, other stylesheets: the definition is ready for both, the form is not); a search endpoint that answers JSON, and a real search page; the permission of a hit per record, not per type; a multi-file rebuild is tested only by one chunk (DuckDB starts a new file after 2,048 rows at the earliest) and a repository with no records gets no batch, so a stale index there stays stale; a failed rebuild leaves its `.building-` directory until the next swap; the RDF/XML that is not well-formed (above); validating a record's graph against its record shape.

### Docs (built 2026-11; `docs.py`, `types/type/doc/doc-base-01.xsl`, `views/docs.py`)

A **doc** is a JSON object made of a record by XSLT: the deep RDF/XML of the record (what the graph cache holds) in, the doc out. It is kept in LMDB and is what Tantivy will be fed from, so the stylesheets that make docs are separate from the index schema (Tantivy drops fields its schema lacks, without a word, measured), and a schema change is a rebuild of the index from cached docs, no XSLT.

- **Stylesheets live in the type folders**, like the SHACL files, in `doc/` as `doc-<profile>-<revision>.xsl` (`assets.DOC_NAME`). The TypeType holds the base, `doc-base-01.xsl`; another type has one that `xsl:import`s it (`href="type:type/doc/doc-base-01.xsl"`, resolved by `xslt.type_catalog`) and adds fields (`types/person/doc/doc-full-01.xsl`: `given_name`, `family_name`). `gracia:docTemplate` of a type record is the file name (a select over `doc/` on the type's manage page, `predicates/gracia_doc_template.py`; none: the doc of the base). A content type names one with `"doc"` in its `TYPE`. `gracia:schema` was renamed **`gracia:schemaTemplate`** (`uri.SCHEMA_TEMPLATE`, `predicates/gracia_schema_template.py`, the form field is `schemaTemplate`); the Python attributes (`Type.schema`, `ContentType.schema`, the job parameter `schema`) keep their names.
- **Dispatch by template, not by function.** The root template loops over the records of the `records` parameter and does `xsl:apply-templates select="$record" mode="doc"` inside `xsl:try` (a record that fails is `{"record", "error"}`). The base template (priority -1) matches every record (`rec:`) and makes the fields every doc has: `record_id`, `record`, `type`, `slug`, `label`, `text`, `resource_uri`, `published`, `modified` (a field with no value is left out; search needs these to filter by what the caller may see). A type's template matches **the uri prefix of its records** (`rec:person:`), calls `xsl:next-match` for the base map and merges its own fields. The base has helpers (`doc:resource`, `doc:literals`, `doc:values`, `doc:fields`). `text` never has a `gracia:credentials` (the old `index.xsl` put the password hash of a user in it). Dates are ISO strings; they become `datetime` when a doc goes into Tantivy (`_for_tantivy`, by the schema).
- **One roll-up per repository.** `docs.rollup` is a generated stylesheet that `xsl:import`s the base and the `docTemplate` of every type (`import`, not `include`: the base is reached by many paths); a template whose file is missing or is named wrong is left out and logged, the other types go on. One Saxon run per batch, no grouping by type. A type's own stylesheet also works alone.
- **Compiled once per generation** (`xslt.Compiled`: the processor, the executable and a fingerprint, a hash of the roll-up and the text of every file it imports). **All of it lives on one thread, `xslt.owner()` (named `saxon`, 64 MB of stack):** SaxonC is a GraalVM native image whose objects belong to the OS thread that made them, and the cache is used by the worker thread and by requests, so compiling, running and releasing are handed to that thread (`Compiled.transform` waits for the result; the runs take turns there, and `Compiled.threads` lets a test see that it is only ever one). A crash of the server ("Fatal error: StackOverflowError … wrong IsolateThread") made us do this; **the cause was not reproduced** (the old design survived a soak of 5 threads on 2,500 real records), so it is a precaution against one class of causes. GraalVM's handler reports *any* segmentation fault of the process (Tantivy, DuckDB, LMDB) in those words, so `xslt.arm_crash_report()` enables `faulthandler` after SaxonC starts: the next fatal signal first prints the Python stack of every thread. SaxonC resolves imports when it compiles (measured: an edit of an imported file is not seen by an executable compiled before). `Cache.compiled(repo)` keeps it next to the etags and `Cache.check` drops it when the repository's time moved, in every process, so a write of a type record, an import or a file-by-file override takes effect after the next write and nothing hooks type changes. A recompile after a write is lazy. To measure with a repository of many types.
- **`DocStore`** (`cache.py`, LMDB, its own directory `<cache dir>/docs`, a `GraphStore` that is stamped twice): key `repo\0` + record id (4 bytes); value: the etag of the graph (16), the fingerprint (16), the JSON. Another etag or fingerprint is a miss. Docs are kept only when there is a cache directory (`Cache.keeps_docs`).
- **Built in `deliver`** (`actions._make_docs`), from the same datasets as the graphs, one run, `keep_docs` in one transaction, the docs of deleted records forgotten with their graphs; `RecordsChanged.docs` has them by record uri. **A stylesheet that does not compile is logged and the batch goes on without docs** (a cache must not stop the queue). `Cache.doc(repo, record_id, record_uri)` does what `Cache.graph` does (kept, or made and kept); `GET <record>/doc` shows it (permission `manage`).
- **Search uses docs (built):** `index.xsl`, `IndexDefinition.stylesheet`/`types`, the same settings of the Search extension and the debug view `<record>/index.json` are gone; `<record>/doc` is the view of a doc.
- **The schema mode and the Search tab (built).** The same doc stylesheets say which fields their docs have: with the parameter `schema=true` the roll-up takes `<types><type slug="person"/>...</types>` and gives an array of fields (`name`, `type`, `stored`, `indexed`, `fast`, `tokenizer`, as `search.Field.as_dict()`, and `types`, the slugs whose docs have it, and `conflict` when two types say it differently). Templates of the mode `schema` dispatch like the doc templates (`/types/type[@slug='person']`, `xsl:next-match`, `doc:field(name, type, options)` makes a field with the defaults). `docs.schema`, `Cache.schema_made`. **Parameters are cleared before every run** (`Compiled.transform`; a SaxonC executable keeps them, and `schema=true` stayed set for the next docs run). `search.compare(offered, definition)` gives a row for each field with a state: `indexed` (in both, the same), `different` (the settings have it otherwise: `differences`), `available` (only the docs have it: greyed, **Add**), `orphan` (only the settings have it: no stylesheet makes it, **Remove**). The comparison is against the **settings of the Search extension**, so Add and Remove edit them (`SearchExtension.add_field`, `remove_field`; the lock "the definition is fixed for now" is gone, so the form and an import can change the fields too) and the index is stale until the job Rebuild search has made it again (the tab says so and has the button). `search.REQUIRED_FIELDS` (`record_id`, `record`, `type`, `published`: a record is deleted by its id, and a hit needs them) cannot be removed. `RECORDS` lost its unused `data` field. The tab is `RepositoryManage.pane_search`, `post_repository_search` (one form of Add/Remove buttons for each index) and `repository_tab_search.pt`; a doc stylesheet that does not work is a message on the tab. **Statistics:** Tantivy-py has no per-field figures; `Indexes.field_stats` counts the documents that have a value with `exists_query`, which works only on fast fields (the others show a dash). A test keeps the two descriptions from drifting: every key of a real doc is a field of the schema mode.
- **Not built:** per-field settings in the stylesheets beyond the defaults (the Add button takes the field as the stylesheet declares it; the form changes it after); whether the Pyramid event is needed at all once docs are in LMDB (search could read from there); a "reload stylesheets" action for an edit of a file on disk; the Rebuild job does not keep the docs it makes in LMDB.
- **A bug met on the way (fixed):** after a type was saved with the manage form, `GET /library/person/manage` answered 301 to `/library/type/person`. The type record had a slug by then, and `TypeManage._record` looked it up with `repository["type"][<number>]`, which redirects a number to the slug of a record that has one; the redirect is an exception and left the view. It uses `Type.by_number` now (`ManagePageAfterSaveTest`). Any other code that finds a record by number in a view should use `by_number` too.

## Performance notes (measured, one 32-core machine, small uniform resources)

- **Import:** about 2.3 s per million triples (parse 0.5 s, row building and appender 1.35 s, SQL 0.43 s). The Python row loop is about 60% of it.
- **`get`:** 8 ms for one resource at 200,000 resources (800,000 rows), after the lookup macros were limited to the dictionary rows they use (it was 24 ms and grew with the dictionary). A hand-written lean query takes 2.7 ms.
- **Sorting and row groups:** sorting `triples` by `s_uri` and row groups of 122,880, 16,384 or 2,048 changed `get` by under 1 ms at this size (reading one resource's rows: 0.84 ms unsorted, 0.69 sorted, 0.57 with 2,048-row groups). Re-measure at a few million resources, and plan a periodic re-sort if it pays.
- **`put`:** about 22 ms fixed plus 0.05 ms per resource (1 resource 23 ms, 10 resources 28 ms, 100 resources 41 ms, 1,000 resources 71 ms). Each big macro costs about 6.5 ms even on empty input, so batch writes. Options if single-put latency matters: a fast path without blank nodes, simpler macros, fewer statements.
- **Since then** a write also runs the triggers of `records` and `history`, the refresh of the etags and the sort of the etags table; the figures at 1,000,000 records (about 0.5 s a record written, 2 ms to 14 ms a page of a listing, 0.5 ms an etag) are in the section on etags. The numbers above are from before that and from small repositories.
- **Scaling:** one process, 1 to 8 threads: 152 to 705 gets/s. Quack clients, 1 to 8 processes: 130 to 638 gets/s. Quack costs about 1 ms per get.

## Rough sequence

Each step is a small increment with its own tests; the order can change.

1. **Content types and validated writes (library).** A content type is data: a class, its shapes, and how its ids and URLs are formed. `put` validates against the shapes of the content type. Decide how new resources get their URI. One write lock.
2. **HTTP API and read records.** The tree grows to `/<repo>/<type>/<id>`, content negotiation, error responses, request size limits. HTML through the existing XSLT chain.
3. **Users, groups and permissions.** Sessions and API keys, default deny (403 for what a caller may not do, 404 for what they may but does not exist), CSRF for cookie sessions, a bootstrap for the first admin. Nothing is deployed before this.
4. **Edit UI.** Deform forms generated from the content type's shapes (`shacl-form` for what the generator does not cover), create and edit records, a small management UI with hand-written Colander forms, and plugin settings forms.
5. **Records.** Revisions, soft delete, state, visibility, embargo and expiry dates, "public now".
6. **Views and caching.** Views per content type (stylesheets with checksums, view permissions), a batch of related resources per record, then ETags and a file cache for anonymous reads. (The ETags and the batches are built, see the section on etags; the stylesheet views and the file cache are not.)
7. **Scale and extras.** Re-sorting tables, single sign-on, and whatever measurement says. (A first search is built: the section on times, caches, the change queue and search; the endpoint and the page for people are not.)

## Ideas worth keeping from the earlier design

- Content types as data, with their SHACL shapes next to them.
- Several repositories, each with its own users, groups and content types.
- Permissions as open-ended names mapped to groups; an admin group with everything; a public group for everyone.
- Records with embedded resources, `revision`, soft delete and a single "public now" rule.
- Rendering from a batch of related resources, selecting by key, never by URI.
- Cache keyed by a hash over the revisions of everything a record reaches; only for anonymous, public renderings.

## Open questions

- **Identity (decided):** the stored subject of every record is its key `rec:<slug>:<n>`, with the number minted per type in SQL; the content is a blank node in it, and `gracia:resource_uri` holds the published name (the ARK of the record unless said otherwise). Still open: how references between records are written (the record urn or the published subject), a `find` that is fast enough for more than rare lookups (it scans the triples table), unique user ids (checked with `find` before a user is created; two simultaneous creations could both pass), and exporting one repository into another (record keys repeat across repositories).
- **Repositories:** now one schema per repository in one file. Revisit if a repository needs its own file (independent backups, or its own owner process).
- **Order:** permissions before the edit UI, or a single-user edit UI first?
- **Shapes in the database (decided):** files in the type packages, see "Types are packages". Still open: shape versions and migrating stored records when a shape changes, because a changed shape applies to every repository at once and existing records may fail it on their next edit.
- **Finding resources:** `Store.records_page` (the records of a type) and `Store.referrers` (the records that point at one) page through the etags table; a `find` by property value is still parked.
- **XSLT safety:** in-process Saxon has no sandbox, which is fine for trusted authors; decide if and when a worker process is needed.
- **Validation limits:** `pyrudof` runs in process with no timeout or kill; decide what protects the server from a pathological shape or batch.
- **Shared blank nodes:** one copy per use is the current rule; decide if it should ever be an error.
- **Backups and the owner:** how to take a consistent backup while the Quack owner runs (an export, not a file copy).
- **Thread-pool sizing and job isolation:** which work gets its own executor or process pool (imports, validation batches, XSLT).
- **API explorer:** a vendored Swagger UI (or similar) for `/<repo-id>/api`, and whether `pyramid_openapi3` is worth adding for the fixed JSON endpoints.
- **Caching plan:** the etags and the listings are built (the section on etags); the extensive plan for the rest (anonymous renderings, a file cache, cache headers) is to be merged in when we get there.
- **Generator coverage:** which shape features the form generator supports first, and whether `shacl-form` is still needed for the rest.
- **Compact JSON representation:** whether to offer a plain JSON form of a resource (and its JSON Schema, derived from the shape) next to the RDF serializations, and what it looks like.
- **Declarative endpoints:** whether a middle path exists between data-only packages and code plugins, for example named, parameterised listings or queries defined as data, so a content type can offer a custom endpoint without Python.
- **Plugin settings scopes:** application-wide, per repository, per content type, and who may edit which.

## Known gaps in what exists

- Import silently drops blank-node structure that no URI reaches (orphans) and empty blank nodes; `put` refuses orphans, import does not.
- Neither import nor `put` validates against shapes unless you call `shacl.validate` yourself.
- No limits yet on triples per resource, nesting depth or request size (only depth 100 and list length 10,000 in the walk).
- No `find` by property value; listings by type and by referrer exist (`Store.records_page`, `Store.referrers`).
- `gracia serve-db` and a `quack:` target work (CLI, web app, tests), but there is no connection pool (one attachment per store: tens of ms of setup per request), no reconnect after an owner restart and no retry on connection errors; `import` over Quack stages through the local-temp push and has only been tried on a small file.
- The web app serves the repository list and figures, the API document, types and records (JSON, RDF/XML, and pages for a browser: the type index with batches and the record), the edit, source and history pages, the manage pages and the jobs. Authentication is HTTP Basic against the users of the repository; there are no cookie sessions yet and no CSRF token on the manage forms of the older pages.
- `gracia serve` is waitress with a few threads, one process; running several processes (gunicorn) with the Quack owner is designed but not tried.
- Read commands on the default repository create `main` when it is missing (the old behaviour); other repositories are never created implicitly.
- Repository names cannot be changed or removed from code (no rename or drop, on purpose).
- A single `get` or `put` has a fixed cost of several milliseconds (see the performance notes); a `put` into a repository of 1,000,000 records takes about 0.5 s with its etags and the sort of the etags table (the section on etags).
- Memory growth of a long-running process (DuckDB buffers, Saxon, `pyrudof`, `pyoxigraph`) is not measured, so worker recycling is not justified yet.
- Whether `pyoxigraph`, Saxon and `pyrudof` release the Python lock is unknown, which decides how far threads scale for XSLT and SHACL.
- Performance on blank-node-heavy data is not measured; the 1M-triple benchmark had none.
- The XSLT nesting stylesheet only reads the flat RDF/XML that `pyoxigraph` writes.
- Repositories made before type packages hold shapes inside their data and have no `gracia:assets`; those made before schemas had names have no `gracia:schemaTemplate`: their types have no form (recreate them). Stored records are not checked against a schema when the type switches to another: the forms of a smaller profile just show fewer fields and keep the rest. A type package that is not installed in a process is skipped with a warning, and a stylesheet cannot be changed at runtime without a deploy.
- The form generator covers one text field per property. No other datatypes, no `sh:in`, no nested shapes, no repeating values, and the saved data is checked by Colander only, not by `shacl.validate`. The manage form has no CSRF token yet.
- Existing repositories (made before records, types and users existed) have no repository resource, no `ids` table and no users: `/manage` fails for them, types are empty, and nobody can log in. `main` created implicitly is the same. A migration or a `gracia repo init` is not written.
- Managers can edit users, and the user form does not yet have a membership field. When it gets one, changing a user's groups must need `manage`, not `super_edit`, or a manager could make themselves an admin.
- Records can be read, listed, edited and added but not deleted (deleting is left for later: other records may point at the record, and its number is never reused). A user made with the add form is in no group, and the forms have no way yet to put a user in `admin` or `editor` (no repeating or URI fields): that is done in the data for now. Types cannot be made through the web (the form cannot fill in `gracia:class`), and a new type has to be added to `gracia:types` by hand. The forms have no repeating values (a user's groups, `foaf:knows`), no URI fields, no dates or numbers, no nested shapes; saved data is checked by Colander only, not by `shacl.validate`, and there is no CSRF token. `gracia:subject` is stored but nothing uses it yet (no rewriting on export, no lookup by subject). No `gracia:public`, embargo or files.
- No plugin settings mechanism or controller layer yet: the view talks to `Store` and the dataset directly.
- A derived integer column for the subject (`type number × 10⁹ + record number`, `BIGINT`, nullable, filled by the loader, the table sorted on it) is parked: measured on 10M rows it made "all persons" 1.9 ms against 6.6 ms for the sorted string `rec:person:`, and the file 88 MB against 142 MB (one row per record, the worst case for strings). The key is the identity and stays a uri; the column can be added later without changing anything around it.
- The table is only sorted by `gracia sort` (a load or a save appends at the end), so there is no job that does it by itself yet; it would be a stage or a periodic job.
- A repository made with the old layout (`urn:gracia:`, integer ids, a `terms` table, `kinds`) cannot be opened by this version; there is no migration (none exists to migrate). Recreate it.
- A repository made before the queue and the sizes (before `actions_queue`, `records.bytes`, `etags.bytes` and `closure_bytes`, the deterministic blank node labels) is not patched up either: recreate it. Records written before the labels keep uuids in `source` until they are written again.
- The Tantivy index is only fed by changes after it was made: an index that was not there before the records needs the job Rebuild search. Records written while the Search extension is off are not in it afterwards either (the same job).
- The search page checks what a caller may see per type, not per record, and the index holds every record (unpublished ones, private types): do not offer the index to anything but that page.
- A repository made before the etags (before the `etags` tables, the `records` columns `created_at` and `is_published`, the numeric `sort_key`) is not patched up when it is opened: the tables are made with the schema, once, and the first write to an older repository fails on the missing table. Recreate it, like the one above.

- **Namespace prefixes: the `ns_prefix` extension** (`extensions/ns_prefix.py`, always on, tests in `tests/test_prefixes.py` and `NsPrefixTest`). It is only a setting: `prefixes`, a list of `{prefix, namespace}` (a sequence widget in the Extensions tab) in the repository record, with `DEFAULT_PREFIXES` (rdf, rdfs, xsd, owl, dc, dcterms, foaf, skos, gracia) as its default, so it is exported and imported with the other settings. Nothing else is on the class: code that needs a dict makes it from the list (`Graph.select`, `cli`). What makes this cheap is that **`Extension.settings` is cached** for as long as what the repository says of its extensions is what was read (a copy of the top level is returned; a change reads again). The prefixes are used by the exports (`Store.used_prefixes(prefixes)` keeps those whose namespace starts a stored URI), the XSLT, `gracia prefixes` (list, `NAME=URI`, `--remove`) and the SPARQL queries. **They are discovered when a file is imported:** `gracia import` adds the prefixes a file declares that are not there (one write), never re-binds one that is there (the clash is a warning) and skips the empty prefix. The `prefixes` SQL table is gone, so **a plain triple store, a database without a repository record, has the defaults and keeps nothing** (`-p NAME=URI` still works). Not built: Turtle submitted through the web (it would add the declared prefixes the same way). The namespace of `gracia:` is `uri.GRACIA_NS`.
- **The URIs the code names: `gracia/uri.py`.** `from gracia import uri` and `uri.LABEL`, `uri.RESOURCE_URI`, `uri.TYPE_CLASS`, `uri.RDF_TYPE`: plain strings, one definition each, so a misspelt name fails when the module is imported (a misspelt URI built on the fly would just match nothing). They are built from `NS`es (`uri.NS`, `G_NS.label_query` or `G_NS["class"]`, a plain object, not a `str`, so `G_NS.title` is not `str.title`): `G_NS` (gracia), `RDF_NS`, `SH_NS`. The stored terms keep their names (`label_query`, `resource_uri`, `memberOf`). Other code that needs a namespace of its own makes an `NS` too.
- **Not built: validation of a record against its record shape.** The record shape, with the content shape embedded, is also what an import (or the validate job) should check a whole record against; the validate job still checks the content against the shape file of the type only. Predicates of an extension that add a field to the form need the extension to contribute a property shape; for now a field is there only if the shape has it.
- **The Predicates tab** of the manage page of a repository (`views/manage.py`, `templates/repository_tab_predicates.pt`, order 40): a card for each registered predicate, like the Extensions tab. The title and the description are the `sh:name` and `sh:description` that the record shape or a type's shape gives the property (the first that names it; the local name of the URI when none does), then the URI of the property, how many values of it are stored (one `GROUP BY` over the table, about a millisecond per 800,000 rows; a property whose value is a blank node, such as `gracia:resource`, counts 0, because those edges are not rows of their own), the predicate's own docstring, the class and a badge for each part it has (`schema_node`, `on_write_sql`). The Types tab is cards in the same way: the name (with a *system* badge), what the shape of the type says of itself (the `sh:description` of its node shape, which each shape file we ship has), the slug, how many records the type has (the same kind of count, `Store.count_by_object`) and a link to its manage page. The tab reads the registry, so it shows what the application knows, not what the repository uses.
- **The source of a record** (`views/record.py`, `templates/source_form.pt`, `static/scripts/source.js`; tests in `tests/test_source.py`). The edit and add pages have a **Source Edit** link above the form, at the right, to `?source=turtle`: the same page with the data of the record as text in place of the form (a **Form Edit** link goes back), a list of serializations (turtle, the default, ntriples, rdfxml, jsonld) and Save. Choosing another format (the button *Show*, which `source.js` presses when the list changes) shows the text in that format; what was typed is parsed first and kept, and the text is read in the format it was shown in (`source_format_was`), so changing the list and pressing Save does not mix them up. The text is highlighted by `editor.js` (turtle and ntriples with the SPARQL mode, rdfxml with the XML mode, jsonld with the JSON mode). Turtle and rdf/xml declare only the prefixes of the repository (`ns_prefix`) that the text uses, found by looking at the text with strings and IRIs left out (`rdf:` is gone from turtle, where `rdf:type` is written `a`); rdfxml is then run through the stylesheet that nests it (`xslt.nest`, about 3 ms: blank nodes go inside the property that points to them, so the content is inside `gracia:resource`), and jsonld is indented; the triples are sorted before they are written (the resource before blank nodes, the type of each first, then property and value), so the same data is the same text and the serializers write typed nodes (the serializer writes one line). `gnarly` (a turtle pretty-printer on pyoxigraph: types first, nested blank nodes, sorted; 0BSD, no rdflib) was tried and not taken: its metadata asks for Python 3.13 (it ran on 3.12 in a small test), its Python API is undocumented (the CLI is the interface) and it was about 3.6 times slower than pyoxigraph's serializer per small record. **Saving** parses the text (an error is shown with the text kept), checks that it is this record and only this record, of this type (other resources are refused), runs the write hooks (so a missing label or ARK is made first), and then checks the result against the shape of the record, the record shape with the shape of the type's content embedded (SHACL, `Record.type.shacl_shape()`; the violations are listed once as `property: message`). The record shape also says that the content has to be of the class of the type (`sh:class` on `gracia:resource`, added from the type's `gracia:class` when the shapes are combined, `assets.record_shape`, not written in any shape file): the shape of a type only picks the nodes that are of its class (`sh:targetClass`), so without it a content retyped to `foaf:Prson` would not be looked at, and only then stores it with `Record.save`. A new record is shown under the placeholder `rec:<slug>:0`; the number is minted only after the text has passed the check on a trial copy (a refused text uses no number) and replaces the placeholder. What is never shown (`Record.hidden`: the credentials) is left out of the text and kept as it was when saving. A class can turn it off with `source_editable = False` (users, whose id is checked and whose password comes from a field): there is no Source link, and `?source=` shows the form. `Record.check` (checks that need the database) is not run for a text.
- **Closed shapes: a property no shape describes.** SHACL's `sh:closed true` (with `sh:ignoredProperties ( rdf:type )`) makes a property that the shape does not list a violation. The **record shape is closed** (it lists `gracia:type`, `gracia:resource_uri`, `gracia:label`, `gracia:slug`, `gracia:resource`, `gracia:is_published`, `gracia:created_at` and `gracia:modified_at`, so a misspelt property on the record is an error). A type's content shape is closed **per profile**, in its shape file: `Person-full-01.ttl` is closed, `Person-minimal-01.ttl` is not, on purpose, because what the minimal form cannot show is kept (a record keeps its `foaf:mbox` when its type goes to the minimal profile), and closing every profile would reject that data; system types stay open (the repository content has the extension blank nodes). The Source Edit view and the validate job show it as `property: this property is not described by the shape (its value is ...)`, once each; the note that the content does not conform to its shape (`sh:node`) is left out when the violations inside are listed. A profile of another type is made strict by adding the two lines to its node shape.
- **`gracia/utils/` is a package of helpers that depend only on leaves** (`uri`, `graph`, the libraries, one another), one module each: `passwords` (salted scrypt hashes), `xslt` (Saxon: nest, render, transform) and `assets` (the files of a type: asset specs, shapes, versions, `record_shape`, and `using(registry)` for code that runs outside a request). Nothing is re-exported by `gracia.utils`: a caller names the module (`from gracia.utils import passwords`). `static.py` stays at the top: it is web infrastructure. `uri.py` stays at the top and holds `NS` (the URIs of a namespace as attributes).
- **`Graph`** (`gracia/graph.py`) is a pyoxigraph Dataset with what gracia does with one, wrapped and not subclassed (pyoxigraph's classes cannot be): `Graph(dataset)` holds the dataset without copying it, `Graph.of(quads)` makes a new one, `Graph.parse(text, fmt)` reads a serialization (`ParseError`), and a graph iterates over its quads, so it goes where quads go; the other attributes are the dataset's (`add(quad)`, `discard`, `quads_for_subject`, ...). A `str` is a `NamedNode` where a subject or a predicate is asked for. Reading: `objects`, `value`, `subjects` (the resources), `extract(uri)` (a resource: its quads and those of the blank nodes below it), `orphaned_nodes()` (quads that belong to no resource: `Store.put` refuses them) and `walk_list(head)` (the items of an rdf list). Changing: `replace(s, p, new)` and `add_value(s, p, o)` (in the graph name of the subject, else the default one; `add` stays the dataset's), `without(predicates)`, `remap(old, new)` and `patch(before, after)` (what was done to a copy, done to this) make new graphs or change this one as said. Text: `serialize(fmt, prefixes)` gives the same text for the same triples (the type of a resource first, so that a serializer writes a typed node), declares only the prefixes it uses in turtle and rdf/xml, nests rdf/xml with the stylesheet and indents json-ld. SPARQL: `select(query, prefixes)` runs one SELECT on the graph (no `SERVICE`), `Graph.validate_select(query, prefixes)` says why a text cannot be run, remembered per text. SHACL: `validate(shapes, shape=None)` checks the graph against shapes (a file, Turtle text, a graph or a dataset) with pyrudof, which is loaded when something is validated (about 30 ms), and gives a `Report` of `Violation`s (`ValidationError` carries one). Rows: `Graph.of_rows(rows)` and `graph.rows()` convert to and from the store's staging rows, and `streaming_parse(source, fmt, prefixes)` and `streaming_serialize(rows, fmt, output, prefixes)` read and write files row by row without holding them (imports and exports); `guess_format`, `rdf_format`, `OUTPUT_FORMATS` and `INPUT_BY_EXTENSION` name the formats. The module that held those, `rdfio.py`, and `shacl.py` are gone. `Store.get` returns a `Graph` and `Store.put` takes a graph or a dataset; a record keeps its data as `record.graph`.
- **Class views: `views.View` and `views/record.py`.** `gracia.views.View` is the base of the class views: it has the request, the context, the store and the repository, a `values()` that a subclass can add to for every page it renders, and `render` and `render_form`. `RecordView(View)` in `views/record.py` is the generic edit and add pages as its two methods, `edit` (context `Record`, permission `edit`) and `add` (context `Type`, permission `add`), each decorated with `@view_config`; the form, the source of the record and saving either are its other methods, and `new` says which page it is (an add page works on a blank record of the type, whose number is made when it is first saved). A record class that wants a page of its own subclasses `RecordView`, overrides what is its own and is registered for its class with `config.add_view(Cls, attr="edit", context=RecordClass, name="edit", permission=...)` (and `attr="add"` for the type); `add_record_class` does that with `RecordView` itself when a class asks for other permissions.
- **The helpers of the source view are methods of the record and of the type, not of the view**: `Type.placeholder` and `Type.skeleton()` (the text of a new record), and `Record.shown_graph()`, `with_hidden_kept(graph)`, `structure_problems(graph, subject)` and `shape_problems()`. `RecordView` keeps what is about the page: `FORMATS`, `EDITORS`, `SourceError`, `known_format`, `subject`, `check_source` and `commit_source` (a subclass can change what is checked and how it is stored). `gracia/source.py` is gone.
